- 새 의존성·환경 변수·빌드 설정·API 계약·DB·auth·상태관리·라우팅 구조를 변경하지 않는다. 필요하면 근거와 구체 변경안을 제시하고 별도 승인받는다.
- 기존 경로의 로딩 방식 최적화는 후보이며, 새 경로·라우팅 패턴을 만들지 않는다. 기존 lazy/Suspense 방식만 재사용한다.
- E01/E06의 전체 합계·정렬·결과 필터를 일부 페이지로 대체하지 않는다. ADR-0009의 기본 페이지 크기·전체 수집 결정을 임의 변경하지 않는다.

- 읽기 전용 실서버 측정이 기본이다. 출석·응모·게임 제출·관리자 발표 등 반복 쓰기를 운영에 실행하지 않는다. 이 동작의 통제 실험은 계약에 맞는 고정 응답으로 분리하고 실서버 성능으로 표시하지 않는다.
- 기존 lint·format 경고의 무관한 자동 수정, 머지·배포는 범위 밖이다.

## 측정 설계

### 환경과 재현 조건

- 개발 서버가 아닌 `npm run build` 결과의 로컬 preview를 사용한다. MSW 비활성·기존 시연 계정 공급·실제 API 프록시를 기존 방식으로 실행하고 .env를 덮어쓰지 않는다.
- Playwright/Chromium이 기존 실행 환경에 있는지 승인 후 확인한다. 없으면 새 의존성을 설치하지 않고 도구/런타임 확보에 필요한 승인을 요청한다.
- 실제 CPU 모델·논리 코어·메모리·OS·Node/npm·브라우저 버전·headless 여부·Git SHA·변경 diff 식별·측정 시각(KST 포함)·API origin·데이터 건수·viewport를 원시 결과에 저장한다.
- 기본 모바일 390×844, CPU 4배 저하, 네트워크 다운로드 1.6Mbps/업로드 750Kbps/지연 150ms로 고정한다. 데스크톱 1440×900·CPU/네트워크 제한 없음은 별도 보조 실험으로 집계한다. 조건을 섞어 p95를 계산하지 않는다.
- 브라우저 측정에서 프록시로 우회한 API에 CDP 제한이 적용되는지 검증한다. 적용되지 않으면 API 지연을 제한했다고 표시하지 않고 프록시 왕복과 브라우저 자원 제한을 별도 기재한다.
- 동일 등록 USER·동일 데이터 ID·건수·서버 상태·빌드 옵션·브라우저·직렬 동시성 1을 전후 유지한다. 변동 시 해당 표본을 조건 불일치로 분리한다. 서버 캐시를 비웠다고 가정하지 않는다.
- 초기 진입은 매회 새 context와 비어 있는 HTTP/Query 캐시로, 전환·재방문은 같은 context에서 수행한다. 재방문 간격은 5초와 35초로 분리한다.

### 표본·중복 요청·지표

- 사용자 추가 승인에 따라 화면별 초기 진입/전환/5초 재방문/35초 재방문은 1회×3배치, 조건당 n=3(워밍업 0회)을 전후 수집한다. 홈 추가 검증은 배치별 워밍업 1회를 제외한 10회×3배치(n=30)다. 다음 페이지가 있는 화면의 페이지 이동도 n=3으로 측정하고, 데이터/직접 링크가 없는 경우 실제 n과 사유를 명시한다. 목록이 모달을 여는 미션은 모달 열기를 별도로 측정한다.
- p95는 오름차순 표본의 `ceil(0.95*n)`번째 값(1부터), 함께 p50·최솟값·최댓값·배치별 p95를 기록한다. 실패/timeout은 삭제하지 않고 건수·원인·완료율로 보고하며 성공 표본 p95임을 명시한다.
- 로딩은 FCP·LCP(초기 탐색, 관측 종료 시점 명시)·DOM 준비·업무 결과 표시를 분리한다. SPA 전환에 navigation LCP를 재사용하지 않는다.
- API 시간은 각 request 시작→response body 수신 완료의 클라이언트 관측 왕복이다. TTFB·body 완료를 구분한다. 화면 동작→업무 결과 paint와 별도 열로 보고하고 병렬 요청 시간을 단순 합산하지 않는다.
- 요청별 메서드·정규화 경로/페이지/필터·사용자 별칭·시작/종료·상태·bytes·실험 구간을 기록한다. 동시 동일 입력, 마운트/전환/재방문 재조회, 무효화, 정상 30초 폴링, 페이지 수집, 429/실패 재시도를 구분한다. 동일 URL이라는 이유만으로 정상 폴링을 중복으로 세지 않는다.
- 홈에서 별도 65초 체류 3회로 폴링 요청 수를 확인하고, 종결 상태 중단은 기존 회귀 테스트와 구분해 기록한다. 이벤트·응모·결과 건수에 따른 E01/E06/E09 비용을 기록한다. 실서버에 없는 대량 자료는 계약 기반 통제 데이터로 별도 측정한다.
- 통제 실험은 전후 고정 fixture·응답 지연·데이터 건수를 동일하게 사용한다. 실서버 데이터와 섞지 않고 서버 응답 성능/운영 p95 목표의 달성 근거로 쓰지 않는다.
- API 429 시 Retry-After를 존중하고 배치를 중단/재예약한다. 버스트·부하 테스트로 바꾸지 않는다.

## BE 후속 항목의 기록 형식

각 항목은 현행 계약/요청 수/데이터 건수/화면 p95/FE에서 해결 불가한 이유/제안 계약/정합성 위험/담당 확인 필요를 포함한다. 후보는 E01의 서버 필터·정렬, E06의 전체 합계·결과 필터용 요약, E09의 다건 조회, 공개→화면 반영 2초 목표와 30초 폴링의 차이다. 측정 전에는 후보이며 새로운 BE 구현 요구를 확정하지 않는다.

## 실행 중 확정 사항

- 사용자 추가 승인: “축소 측정 후 주요 화면 30개 검증”. 일반 화면·조건은 1회×3배치(n=3), 주요 검증 화면인 홈은 10회×3배치(n=30)로 전후 비교한다. 홈 추가 검증은 배치별 워밍업 1회를 제외한다. n=3의 p95는 최댓값이며 안정적인 모집단 p95로 해석하지 않는다.
- Python Playwright가 없어 기존 앱 번들의 Node Playwright로 구현했다. 프로젝트 의존성을 설치하지 않았다.
- 제품 코드의 실제 수정 범위는 `src/app/routes/userRoutes.tsx`와 인접 회귀 테스트다. 조회 신선도·전체 수집·무효화 정책은 보존했다.
