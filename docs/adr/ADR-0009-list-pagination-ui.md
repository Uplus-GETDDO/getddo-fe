# ADR-0009: 목록 페이지네이션 UI 패턴

- 상태: accepted
- 날짜: 2026-10-08

## 맥락

spec 공통 계약(`../getddo-spec/05-api/common.md`)은 목록 응답을 `Page<T>`(1부터 시작하는 번호형)와 `Cursor<T>`(불투명 `nextCursor`) 두 가지로 제공한다. 어느 API가 어느 형식인지는 서버가 정한다. 반면 화면이 번호 이동을 보여줄지, "더보기"를 보여줄지는 FE가 정할 수 있다. 현재 코드는 다음처럼 섞여 있다.

- 관리자 이벤트 관리: `Page<T>` + `shared/ui/pager` (기존 공통 감사 화면은 과거 구현이며 공용 ADR-024로 이번 제공 범위에서 제외)
- 알림: `Cursor<T>` + `useInfiniteQuery`
- 응모권 이력: `Cursor<T>`
- 내 응모 내역·이벤트 목록: `Page<T>`를 전부 모아 한 번에 표시

## 결정

화면 유형으로 UI를 정하고, 응답 형식은 entities 쿼리 훅이 흡수한다.

| 화면 유형                                                     | UI                                 | 비고                                                                                                                                                                                           |
| ------------------------------------------------------------- | ---------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 관리자 테이블 (차단 내역, 이벤트·사용자 관리, 추첨 실행 이력) | 번호형 `Pager`                     | 특정 페이지 이동·건수 확인이 필요하다                                                                                                                                                          |
| 사용자 시간순 피드 (알림, 응모권 이력)                        | "더보기" 버튼 (`useInfiniteQuery`) | 모바일·큰글씨 모드에서 번호 버튼보다 조작이 쉽다. 자동 무한 스크롤은 쓰지 않는다 — 접근성·푸터 접근 문제                                                                                       |
| 사용자 전체 표시 목록 (이벤트 목록, 내 응모 내역 등)          | 전부 모아 표시                     | 현재 방식 유지. 내 응모 내역은 화면이 응모 건수·사용 응모권 합계를 전체 내역으로 집계하므로 모든 페이지를 모은다(아래 결과 절). 이벤트 목록은 항목이 100건을 넘으면 "더보기"로 전환을 검토한다 |

- `Page<T>` API를 "더보기" 화면에 쓸 때는 `useInfiniteQuery`의 `getNextPageParam`에서 `page * size < totalElements`로 다음 페이지를 계산한다. 화면은 응답 형식을 모른다
- `Cursor<T>` API를 번호형으로 보여주지 않는다 — 커서는 임의 페이지 이동을 지원하지 않는다. 관리자 화면 API가 커서로 확정되면 그 화면만 "더보기"로 바꾼다
- `Page<T>`의 필드는 `items`·`page`·`size`·`totalElements`, `Cursor<T>`는 `items`·nullable `nextCursor`·`totalElements`다. `totalPages`·`hasNext`는 응답 필드가 아니다. 공통 `common.md`의 size 기본 20·범위 1~100은 제안이며, 개별 채택·현행 계약에서 명시한 값은 해당 API 기준으로 적용한다
- FE 기본 페이지 크기는 20을 쓴다. 전부 모으는 목록은 개별 API 허용 범위 안에서 목록별 상수를 유지한다 — 이벤트 목록 `EVENTS_PAGE_SIZE` 20, 내 응모 내역 `ENTRIES_PAGE_SIZE` 50, 미션 목록 `MISSIONS_PAGE_SIZE` 50 (현행 유지, 이 ADR에서 바꾸지 않는다)

## 결과

- 응답 형식이 바뀌면 entities 쿼리 훅에서 흡수하되, 임의 페이지 이동이 불가능한 `Cursor`로 바뀐 관리자 화면은 위 결정대로 "더보기"로 전환한다. 공통 감사 화면은 제공하지 않으며 추첨 업무별 이력만 `05-api/drawing.md`의 페이징 경로를 따른다
- 내 응모 내역은 이 ADR에서 "더보기"로 전환하지 않는다 — `useMyEntries()`가 모든 페이지를 모으는 계약을 유지한다. 일부 페이지만 불러오면 `MyEntriesPage`의 응모 건수·사용 응모권 합계가 불완전해진다
- 후속 검토: 응모가 쌓여 요청 수가 문제가 되면, 합계를 서버 집계(예: 요약 API)로 받는 방안을 BE와 협의한 뒤에만 "더보기"로 전환한다

## 2026-10-20 구현 현황

GD-246에서 T02는 최초 5건과 명시적 커서 더보기로 전환했고 기간 합계를 목록 일부로 계산하지 않도록 분리했다. E01/E06 전체 수집은 남아 있다. 이를 바꾸는 계획은 [통합 로드맵 L5](../superpowers/plans/2026-10-20-backend-integration-roadmap.md)를 따르며, 현재 전체 합계·결과 필터를 보존할 계약 확인 없이 이 ADR의 결정을 뒤집지 않는다.
