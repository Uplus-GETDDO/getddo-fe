# GitHub 레포 정리와 README 개선 계획

> 실행자는 `executing-plans` 스킬로 작업을 순서대로 수행한다. 2026-10-26 사용자가 구현을 승인했다. 기존 자료의 이동·삭제는 수행하지 않는다.

**목표:** GitHub 방문자가 서비스, 구현 기능, 기술적 판단과 실행 방법을 이해하도록 README와 문서 탐색 구조를 정리한다.

**구조:** getddo-fe의 README를 서비스·기술 소개의 진입점으로 삼고, 상세 개발 절차는 CONTRIBUTING.md, 문서 탐색은 docs/README.md로 연결한다. 공용 정책과 API 계약은 getddo-spec을 원본으로 유지한다.

**기술:** 기존 Markdown, GitHub 상대 링크, 기존 검증 명령을 사용한다. 의존성·빌드 설정·애플리케이션 구조는 변경하지 않는다.

**요청 기준:** 발표 전 GitHub 레포 정리와 README 수정·개선을 구상한다. 발표 자료 작성은 포함하지 않는다.

## 현재 확인한 문제

- 작업 폴더 자체는 Git 저장소가 아니며 getddo-fe와 getddo-spec이 별도 저장소다. 백엔드 저장소는 현재 폴더에 없다.
- FE README는 2026-10-21 작업본을 기준으로 남은 연동을 서술하지만 이후 검증 기록과 맞지 않는다.
- README의 자동 추첨 마감 +5분은 현행 공용 정책의 마감 +1분 이후 대상 선정과 충돌한다. 실제 실행 시각과 발표 시각은 구분해야 한다.
- AR01/AR02 계약 미확정·배포 404 설명은 GD-317의 2026-10-23 실측 기록과 충돌한다. 기록은 당시 측정 결과이며 현재 배포 보장으로 표현하지 않는다.
- README의 관련 저장소 링크는 GETDDO 조직을 가리키며 로컬 원격은 Uplus-GETDDO다. 현재 조직 기준으로 대조한다.
- docs/README.md는 과거 로드맵·실행 프롬프트를 주요 진입점으로 소개한다. 형제 저장소 상대 링크도 GitHub에서 사용할 수 있는 주소로 정리해야 한다.
- reports에는 Git 추적 파일이 358개 있으며 plans에는 계획·실행 프롬프트·인수인계·JSON·스크린샷이 혼재한다.
- spec README의 API 계약 전체를 초안으로 소개하는 설명과 PR 반영 원칙은 도메인별 채택 상태 및 해당 저장소의 main 직접 반영 규칙과 대조가 필요하다.
- FE 작업 트리에 기존 계획 파일 삭제 1건과 시연 영상 시나리오 미추적 파일 1건이 있다. 이 계획의 실행에 포함하지 않는다.

## 작업 1: 사실관계와 README 개편

- [x] 현재 코드·공용 명세·검증 기록으로 기능과 제한 사항을 대조한다. 계획만 있는 기능을 구현 완료로 쓰지 않는다.
- [x] README를 소개 및 배포 링크 → 대표 화면 → 사용자·관리자 주요 기능 → 핵심 설계 → 기술 스택 → 실행 방법 → 팀 기여 → 문서 링크 순서로 구성한다.
- [x] 응모권 이력·멱등키·추첨 결과 검증·FSD·상태관리 분리를 실제 코드 또는 ADR과 연결해 설명한다.
- [x] Jira 작업별 나열, 오래된 남은 작업, 긴 협업 규칙은 README에서 덜어내고 해당 기준 문서로 연결한다.
- [x] 팀원 이름과 역할은 확인된 자료만 사용한다. 실계정 UUID·시연 계정 JSON은 공개 문서에 복사하지 않는다.
- [x] 문서의 추첨 시점·가상 시계·네 게임·배너·차단 조회 설명을 최신 근거에 맞춘다.

## 작업 2: 문서 탐색과 레포 파일 정리

- [x] docs/README.md에서 기준 문서·기술 결정·검증 기록·과거 계획으로 진입할 수 있게 구성한다.
- [x] reports에는 최신 대표 검증 기록을 안내하는 색인을 두는 방안을 우선 검토한다. 358개 파일이라는 이유만으로 일괄 삭제하지 않는다.
- [x] 과거 계획의 완료 여부와 링크 참조를 확인하고, 보관 위치 변경이 필요하면 파일별 이동 목록을 먼저 제시한다.
- [x] node_modules·dist·로컬 스크린샷은 Git 추적 여부를 기준으로 분류한다. 상위 작업 폴더의 파일을 GitHub 레포 오염으로 간주하지 않는다.
- [x] 실행·테스트용 MSW, scripts, public 자산은 참조와 용도를 확인하며 외관 정리를 이유로 제거하지 않는다.
- [x] spec README의 조직명·문서 지도·채택 상태·협업 규칙을 대조해 정리한다.

## 작업 3: 검증

- [x] git diff로 문서 변경과 승인된 파일 이동만 포함됐는지 확인한다.
- [x] README 이미지·상대 링크·앵커가 실제 경로를 가리키는지 확인한다. 저장소 간 링크는 GitHub URL을 사용한다.
- [x] 기록의 측정일·커밋·환경을 유지하고 과거 성능 수치를 현재 배포 수치처럼 표현하지 않는다.
- [x] FE 프로젝트 규칙의 format:check, lint, test:ci, build를 실행하고 결과를 기록한다. 자동 포맷이나 lint 수정은 별도 사용자 승인 없이 수행하지 않는다.
- [x] GitHub About·Topics·기본 브랜치·브랜치 정리·릴리스는 읽기 확인 후 별도 변경 대상으로 제시한다. 브랜치 삭제·기본 브랜치 변경은 이 문서 정리 작업에 묶지 않는다.

### 전체 검사와 로컬 환경의 차이

- 기본 `npm run format:check`는 중첩 로컬 작업트리의 `.claude-worktrees/test-gd-296/public/mockServiceWorker.js`와 기존 미추적 `2026-10-26-demo-video-scenario.md`를 포함해 경고를 냈다. 이번 변경 문서는 포맷을 검증했고 해당 기존 자료는 수정하지 않았다.
- 기본 테스트는 중첩 과거 작업트리까지 수집했다. 현재 코드의 전체 144개 파일은 위 명령으로 중첩 작업트리만 제외해 검증했다.
- 프로세스 방식·2스레드 실행은 출력 없이 지연돼 중단했고, 날짜 유틸 20개 독립 테스트 통과를 확인한 뒤 단일 스레드로 전체 테스트를 완료했다. 테스트 설정 파일은 변경하지 않았다.
- 테스트 중 기존 act·차트 크기·동작 줄이기 관련 경고가 출력됐다. 경고를 숨기거나 테스트·앱 코드를 수정하지 않았다.
- FE는 로컬 `docs/GD-362`, 공용 명세는 저장소 규칙대로 `main`에서 수정했다. 기존 사용자 삭제·미추적 파일은 보존했다.
- 위 구현·검증 시점에는 커밋·push·PR·GitHub 설정 변경을 수행하지 않았다. 이후 사용자 요청에 따라 GD-362로 커밋·push·dev PR 머지·작업 브랜치 정리를 진행한다.
