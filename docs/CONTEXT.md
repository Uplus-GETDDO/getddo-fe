# CONTEXT.md — 도메인 맥락

코드를 만지기 전에 읽는 도메인 용어·코드 매핑과 FE 고유 판단 기준이다.
"어떻게 쓰는가"(코드 규칙)는 [AGENTS.md](../AGENTS.md)가 담당하고, 여기는 "도메인이 코드의 어디에 있으며 무엇을 조심하는가"만 담는다.

**도메인 정책의 기준 문서는 공용 명세 저장소 `../getddo-spec/`다.** 이 파일의 도메인 서술이 spec과 다르면 spec을 따르고, 미확정 정책은 `../getddo-spec/00-requirements/pending-decisions.md`를 확인한다. 기획 맥락(페르소나·유저플로우·비기능)은 [product-context.md](product-context.md)를 읽는다.

## 서비스 핵심 원칙

**"검증 가능한 공정한 추첨"**이 이 서비스의 존재 이유다. 실행별 명단·응모권 수·가중치·조건 스냅샷과 확정 결과를 보존하고 관리자가 인원·후보 유효성·중복 당첨·실행 이력의 정합성을 검증한다. 시드·입력 순서 보존과 난수 재실행으로 같은 당첨자를 재현하는 요구는 없다(`03-decisions/001-drawing-consistency.md`, `02-domain/drawing.md`). 이미 확정된 동일 실행의 재요청에는 저장된 결과를 반환한다. 응모권 이력은 수정·삭제 없이 누적하며 이력과 현재 보유 응모권 상태가 항상 일치해야 한다. UI를 만들 때 "이 화면이 불투명해 보이지 않는가"를 기준으로 삼는다.

## 이벤트 상태 전이

상태 목록과 전이 조건의 원본은 `../getddo-spec/02-domain/event.md`다 (`진행 예정 → 진행 중 → 마감 → 추첨 결과 확정·발표 대기 → 결과 발표 완료`, 별도 상태로 `취소`, `재추첨`). 이벤트 일시 중단·재개는 2026-10-06 `getddo-spec` ADR-015로 제외됐다 — 중단 상태·중단 시각·중단/재개 조작을 새로 만들지 않는다. 어뷰징 전원 제외로 끝나는 '추첨 대상자 없음'(`NO_ELIGIBLE_ENTRANTS`) 종료 상태도 2026-10-11 ADR-018로 신규 사용이 폐지됐다 — 과거 이력의 조회 호환성만 담당자가 별도 검토한다.

현재 `entities/event/model/types.ts`의 `upcoming → open → closed → drawn`은 목업용 단순화다. 실서버 연동 시 spec 상태 체계로 확장해야 하므로, 현재 enum에 의존한 로직을 넓게 퍼뜨리지 않는다.

이벤트 수정·등록 제한 (관리자 폼 구현 시 반영, 원본 `02-domain/event.md`):

- 이벤트 등록과 경품·당첨 인원 등록은 함께 성공하거나 함께 실패한다 — 경품 없이 이벤트만 등록되지 않는다. 같은 등수에는 한 종류의 경품만 등록한다
- 시작 전이며 진행 예정 상태에서만 수정 가능하다. 취소 상태는 시작 전이라도 수정 불가이고, 시작 시각은 앞당길 수 없다(늦추기만 가능). 진행 중·마감 후에는 수정 불가
- 시작 전이며 응모 이력이 없는 이벤트만 삭제할 수 있다. 삭제해도 연결 배너는 자동 삭제되지 않고 관리자가 배너 관리에서 수동 삭제한다 — 삭제·취소 이벤트에 연결된 배너는 사용자 목록에서만 숨긴다(ADR-021·ADR-023)

## 실시간 응모 현황 갱신

요구사항 원본은 기능 요구사항 7절이다. 갱신 주기와 방식은 구현 담당자 재량으로 위임됐고 `05-api/entry.md`는 E03 재조회 제안과 함께 SSE·WebSocket을 필수로 두지 않는다고 명시한다.

- 현황 수치는 **E03 전용 조회** `useEntryStatistics(eventId)`(`entities/entry`)로 받는다 (ADR-0007). 진행 중(`open`) 이벤트만 **30초 폴링**하고, 그 외 상태는 폴링하지 않는다. 홈 배너처럼 여러 이벤트가 겹치는 곳은 현재 보이는 항목만 켠다
- `useEventList`·`useEvent`의 폴링은 현황이 아니라 **상태 전환 감지** 용도다 — 상세는 추첨 완료(`drawn`)까지 폴링한다 (마감 상태는 결과 발표 전환을 감지해야 한다)
- **응모 성공 직후 즉시 재조회**는 `useEnterEvent`의 `onSuccess` 무효화(`['events']`·`['tickets']`·`['entries']`)가 담당한다. E03은 `['entries', 'statistics', eventId]`라 함께 무효화된다
- 표시 지표는 E03의 `participantCount`(접수 완료 응모자의 중복 제거 수)·`totalSpentTicketCount`(그 응모자들의 누적 차감 합계, 반환은 빼지 않음)·`mySpentTicketCount`(본인 누적 차감, 미응모·관리자는 0)다 — 2026-10-14 GD-200으로 현행 구현 기준 확정됐고 거절 이력은 포함하지 않는다. `Event`에는 응모 현황 필드가 없다 (`myEntryCount`는 본인 응모 건수 표시용으로 남아 있다). 당첨 확률은 표시하지 않는다

## 시간 규칙 — 반드시 지킬 것

정책 원본은 `../getddo-spec/00-requirements/functional-requirements.md`의 "공통 시간 기준과 화면 표시"다.

- 서버와 주고받는 시각은 **UTC ISO 8601** 문자열(또는 오프셋 명시), 화면 표시는 `shared/utils/date`의 `formatKst`만 사용한다
- **업무 기준일·기준월은 KST다** — 일일 출석·게임 보상은 매일 00:00 KST에, 연속 출석·응모권 귀속월·만료는 매월 1일 00:00 KST 경계를 따른다. 관리자가 화면에 입력하는 운영 시각도 KST로 해석한다
- **마감·발표 판정은 서버 시각 기준**이다. 마감 전 접수 완료된 응모는 응답이 늦게 도착해도 유효하고, 클라이언트 시각으로 마감 여부를 판정해 버튼을 막는 로직을 만들지 않는다 (표시용 카운트다운은 허용). 서버의 마감 판정은 응모 트랜잭션 커밋 직전의 최종 확인이며, 그 확인과 커밋 확정 사이의 상한이 보장되지 않는 간격 안에 커밋된 응모는 마감 전 접수로 인정한다(GD-205)
- 마감 후 사용자 화면은 **'응모 마감 · 결과 발표 대기'만 표시**한다 — 5분 카운트다운과 고정 발표 예정 시각은 없다(ADR-022). `publicationScheduledAt`은 E08·E09와 이벤트 목록·상세 응답에서 제외됐고, 관리자 응답에만 최초 자동 추첨 기준 시각 `drawScheduledAt`(`endsAt`+5분)이 있다(GD-203)
- 최초 공개는 **관리자 육안 검토 후 발표 요청 한 번으로 최종 확인·전체 명단 공개를 함께 처리**한다 — 별도 확인 버튼·선행 확인 호출·최초 발표의 `publication` 추가 호출을 요구하지 않는다(2026-10-15 ADR-022 보완). `POST /admin/draws/{runId}/result-confirmation`의 INITIAL 확장은 GD-199 PR 기준으로 병합 후 적용 예정이며, 입력·재시도·오류는 `05-api/drawing.md`의 PR 대조 계약을 따른다. 결과 확정·시간 경과만으로 공개하지 않고 스케줄러의 자동 공개·공개 재호출도 없다. 서버가 실제 공개하기 전 결과는 표시하지 않는다
- 시간 판정이 필요한 로직은 `new Date()`를 직접 호출하지 않고 `useVirtualClock().now()`(`shared/model/virtualClock`)를 경유한다 — 관리자 시간 여행(시연)이 오버라이드할 수 있어야 하기 때문이다. 순수 함수는 `now`를 인자로 받는다(`shared/utils/date` 참조)

## 중복 방지·멱등키

"같은 요청의 재시도와 새로운 요청을 구분한다"는 확정 정책이다 (`../getddo-spec/02-domain/entry.md` — 응모권 미사용 이벤트도 동일).

- 응모·미션 제출과 AD05 당첨 취소에는 각 계약에 따라 `shared/utils/idempotencyKey`의 `createIdempotencyKey()`로 생성한 UUID를 `IDEMPOTENCY_HEADER` 헤더(`Idempotency-Key`)에 붙인다. 모든 POST에 일괄 적용하지 않는다
- 작업별 구분은 `05-api/common.md`와 개별 채택·현행 구현 계약을 따른다: 응모·미션=멱등키(응모의 키는 UUID이며 응모 요청 결과(접수 또는 저장된 거절)의 ID로 그대로 쓴다 — GD-134·GD-145), **출석=사용자·KST 기준일 재처리**, **게임=서버 발급 `playId`**, 알림 읽음=사용자·알림 ID. 새 부수효과 요청도 개별 계약에 따라 중복 식별 기준을 확인한다
- 응모·미션의 같은 키·다른 본문은 각각 409 `ENTRY-009`·`MISSION-005`다. 같은 키·같은 본문의 성공 재시도는 저장 결과를 200으로 반환하지만, 저장된 응모 거절은 상황이 바뀌거나 마감이 지나도 최초와 같은 4xx·오류 코드를 반환한다. 목업의 거절 이력 반영 여부는 아래 임시 상태와 구분한다
- AD05의 키는 전역 범위이며 관리자·대상·정규화한 사유가 모두 같은 재시도만 기존 취소·연결 실행을 재사용한다. 다른 관리자·대상·내용으로 재사용하면 409 `CANCEL-003`이다. AD09·최초 재개는 기존 실행 ID로 구분하며, GD-199 최초 발표 PR은 본문·추가 멱등 헤더 없이 최신 검토 `runId`를 사용한다(`05-api/drawing.md`)

## 비공개·마스킹 — FE 고유 책임

정책 원본은 `../getddo-spec/02-domain/drawing.md`(결과 발표)다. FE가 특히 지켜야 할 것:

- **발표 전 당첨 결과는 비공개**다. 재접속·직접 조회로도 노출되면 안 되므로, 발표 상태 확인 없이 결과를 렌더링하는 코드를 만들지 않는다
- 발표 결과는 **마스킹한 이름과 전화번호 끝 4자리**로 표시한다 — 이름은 외자면 성만, 그 외는 처음과 마지막 글자만 드러낸다(예: 김수→김*, 김민수→김*수, 남궁민수→남**수). 이메일은 화면·응답 모두에 포함하지 않는다. 미등록 값의 대체 표시는 이번 범위 제외 (2026-10-14 확정, `02-domain/drawing.md` 결과 발표)
- **당첨 확률은 표시하지 않는다** — 실시간 현황에 표시하는 것은 응모자 수(중복 제거), 응모 건수, 총 차감 응모권 수, 본인 차감 응모권 수까지다
- 등급 응모권(ADR-014·016·025) — 브론즈/실버/골드/플래티넘의 게임·미션 지급 확률은 79.98/18/2/0.02%, 장당 추첨 가중치는 1/3/5/10이다. 지급은 1장, 출석은 브론즈 고정을 유지한다. FE 스키마·화면 맵·등급별 선택/합계·멱등 요청 비교·목업 지급/차감을 네 등급으로 전환했다. 플래티넘 전용 이미지 확정 전에는 은색 그림을 재사용하며 이름·색상 토큰으로 구분한다. BE 적용 시점·기존 응모권 전환·실배포 연동 검증은 후속이며 완료로 해석하지 않는다. 같은 등급 내 만료 임박순 차감과 원래 등급 반환은 유지한다(`05-api/ticket.md`, `pending-decisions.md`).
- 신규 추첨 제외와 제외 사유 안내는 제공하지 않는다(ADR-018) — 본인 결과의 `EXCLUDED`와 '추첨 대상자 없음' 종료 표시를 새로 만들지 않는다. 다른 사용자의 탐지 수치·차단 기록·검증 근거는 비공개
- **관리자 미확인 재추첨 결과는 공개 명단·본인 결과·알림 어디에도 노출하지 않는다** — 최초 공개 전이든 발표 후든 동일하다. 결과 확정·확인 저장만으로 공개되지 않고 명시적 관리자 공개 요청이 필요하다(ADR-022)
- 발표 후 명단 갱신 안내는 **당첨 취소자와 새 당첨자에게만** 생성된다 — 전체 응모자에게 재발표 알림을 보내지 않는다
- 발표 후 취소~공개 갱신 사이의 취소자 임시 표시·본인 중간 결과는, 이번 운영에서 발표 후 취소·재추첨을 사용하지 않는 전제로 GD-140 범위에서 제외다 — 관리자 취소·재추첨 API는 유지되며 해당 운영을 시작하기 전 표시 계약을 보완한다
- 재추첨 진행 과정·연출은 관리자 화면에만 제공한다

## 사용자 역할·시연

`UserRole = 'USER' | 'ADMIN'` (`entities/user/model/types.ts`) — spec과 BE `UserRole` enum의 대문자 표기를 따른다.

- 로그인 화면의 역할 선택은 **데모 전용 사용자 문맥 선택**이다. 별도 로그인·권한 변경 API를 추가하지 않고 서버가 등록된 사용자 ID의 DB 역할·멤버십과 헤더를 대조한다(`05-api/common.md`, `user.md`). 이 헤더 방식은 신원 인증이 아니므로 통제된 개발·시연 환경을 기준으로 한다
- 사용자 역할은 서버가 결정하며, 클라이언트가 보낸 role 값을 신뢰하지 않는다 — 권한 우회용 role 변경 코드를 만들지 않는다
- MSW 개발 환경에서 세션이 `ADMIN`으로 시작하는 것은 목업상 관리자 화면 확인을 위한 편의 장치다
- 관리자는 응모할 수 없다 (임직원 여부는 응모 제한 조건으로 사용하지 않는다 — `getddo-spec` 기능 요구사항)

- 멱등키 생성 주체·전달 방식 — 응모·미션은 UUID `Idempotency-Key`, AD05는 전역 취소 키를 사용한다. 재시도는 키·본문을 유지하고 새 응모·답변은 새 키로 구분한다. 응모 성공 재시도는 200, 저장된 거절은 최초 4xx를 반환한다. 공통 초안의 `IDEMPOTENCY_CONFLICT`는 제안 이름이며 현행 응모·미션 코드는 `ENTRY-009`·`MISSION-005`다. 관리자 생성 요청에 공통 멱등 응답을 약속하지 않는다
- 응답 봉투·페이지네이션·오류 코드 — `05-api/common.md` 전체는 검토 대기지만 현행 봉투는 `success/code/message/data`이며 실패는 실제 4xx·5xx와 `data=null`이다. `Page<T>`는 `items`·`page`·`size`·`totalElements`(page 1부터), `Cursor<T>`는 `items`·nullable `nextCursor`·`totalElements`이고 `totalPages`·`hasNext`는 없다. 공통 size 기본 20·범위 1~100은 제안이므로 개별 채택·현행 API의 값을 우선한다. `COMMON-001`·`002`·`005`·429 `COMMON-006` 및 도메인별 현행 오류 코드를 사용하며 제안 이름과 혼동하지 않는다. `ENTRY-010`·`MISSION-006`·`ATTENDANCE-002`~`005`·`USER-007`과 추첨 조회 `DRAW-QUERY-001`·`002`도 각 도메인 명세를 따른다
- 사용자 문맥 헤더 — 결정(2026-10-12): 모든 업무 API는 등록 UUID인 `X-User-ID`와 `X-User-Role`(`USER`/`ADMIN`)을 필수로 받는다. `X-User-Membership`(`excellent`/`vip`/`vvip`)은 USER의 멤버십 조건 API에서 필수, 그 외 선택이며 전달하면 DB 값과 대조한다. 권한·자격은 DB 값으로 판단하고 헤더로 승격·변경하지 않는다. 필수 문맥 누락은 401 `USER-003`, 미등록 ID는 401 `USER-002`, 역할 불일치는 403 `USER-004`, 필수 API의 DB 멤버십 없음은 403 `USER-005`, 멤버십 불일치는 409 `USER-006`, 형식·빈 값·중복 헤더는 400 `COMMON-005`다(`05-api/common.md`). FE 인터셉터는 `src/app/config/sessionSync.ts`에서 세션 문맥을 주입하며, 전송 구현과 명세·배포의 완료 여부는 구분한다 알림 목업의 `USER_CONTEXT_REQUIRED`는 `USER-003`, 응모 목업의 멤버십 불일치는 `USER-006`으로 갱신했다. 관리자 멤버십 NULL은 FE 헤더 생략으로 우회했으며 DB 근본 해결은 BE 후속이다.
- 당첨자 마스킹 — 2026-10-14 확정으로 해소: 이름은 외자면 성만·그 외 첫·끝 글자, 전화번호는 끝 4자리, 이메일은 공개하지 않는다 (`02-domain/drawing.md` 결과 발표). 미등록 값의 대체 표시는 이번 범위 제외
- 수동 최초 공개(GD-199) — 2026-10-15 확정 정책은 육안 검토 후 `POST /admin/draws/{runId}/result-confirmation` 한 번으로 최종 확인·전체 최초 공개다. 별도 확인 버튼·선행 확인 호출·최초 공개의 AD06 추가 호출은 없다. `05-api/drawing.md`의 PR 대조 계약은 최신 검토 실행 `runId`(AD01의 최대 `runNumber` 실행을 AD02로 검토), 본문·추가 멱등 헤더 없음, 200 `DrawResultConfirmation`을 기록한다. 검토 중 명단이 바뀐 이전 실행은 409 `PUBLICATION-005`로 거절하고 다시 조회·검토한다. 성공 재시도는 최초 공개 버전·확인 기록을 반환하며 공개·알림을 중복 생성하지 않는다(이후 취소·삭제 등 공개 불가 상태는 재시도도 거절). 응답 확인자는 실제 발표자와 다를 수 있어 실제 발표자·시각은 `PublicListChange`와 구분한다. spec의 2026-10-16 대조에서는 PR #108이 OPEN으로 병합 후 적용 예정이며, 병합·배포·FE 연동 완료를 뜻하지 않는다. 나머지 장애 복구·취소 전환, 선택적 `abuseCaseId` 연계, 전체 취소·전체 재추첨은 후속으로 유지한다
- 추첨·결과 API — 사용자 결과 조회는 E08(`GET /events/{eventId}/results`)·E09(`GET /events/{eventId}/my-result`)로 2026-10-14 채택됐다(GD-140). 공개 전에는 `isPublished=false`·빈 `prizes`이고 `publicationScheduledAt`은 응답에서 제외다. 관리자는 AD01~AD09 중 GD-87(최초 재개)·GD-138(AD05 취소·AD09 재개 일부)·GD-169 선택 범위가 확정이며, 최초 발표는 `POST /admin/draws/{runId}/result-confirmation`의 INITIAL 확장으로 최종 확인·공개를 함께 처리하며 GD-199 PR 병합 후 적용 예정이다. 가중치 계산도 `ticketCount` 그대로에서 등급별 장수×장당 가중치 합산으로 바뀌었다(ADR-014) — `ticketCount`(실제 장수)와 `weight`를 구분해 반영한다. 2026-10-11 ADR-018로 `displayStatus`의 `NO_ELIGIBLE_ENTRANTS`, `MyResult.result`의 `EXCLUDED`·`exclusionReason`, `TicketRefund.reasonType`의 `PARTICIPANT_EXCLUDED`가 계약에서 빠졌다 — 신규 코드·목업에 반영하지 않고 기존 값의 조회 호환만 남긴다
- 추첨 관리 목업(GD-125) — `mocks/handlers/draw.ts`가 AD01~AD09 초안을 구현한다 — GD-169로 확정된 범위와 아직 검토 대기인 부분이 섞여 있다(`entities/drawResult`·`entities/winner`의 Zod가 검증 기준, 계약 테스트 `draw.test.ts`). 이벤트별 추첨 상태는 마감된 이벤트를 처음 조회할 때 후보 33명으로 만들고, 최초 추첨(자동)은 확정된 채 시작한다. 당첨 취소(AD05)는 재추첨 실행을 함께 등록하고, 재추첨은 실제 시계 기준 약 1.5초 PREPARING → 약 4.5초 이내 CONFIRMED로 진행한다(화면은 realtime 프리셋 30초 폴링 + 수동 새로고침). 시드: `adm-904`(재추첨 실패 → AD09 재개 시연), `adm-906`(최초 추첨 실패 → 최초 재개 시연), `adm-905`(최초 발표 전 — AD06 비활성 시연), `adm-902`(취소된 이벤트). 추첨 상태는 `adminEvent` 목업의 이벤트 상태(`REDRAWING` 등)와 연동하지 않는다. 최초 추첨을 수동으로 시작하는 API는 계약에 없어 화면에도 없다(마감+5분 자동 추첨). 목업의 자동 최초 공개 연출은 ADR-022로 폐지 대상이다 — 자동 추첨까지만 진행하고 사용자 화면은 '결과 발표 대기'를 유지하며, 육안 검토 후 단일 발표 요청(GD-199 PR 병합·연동 후속)으로 재구성한다. AD05의 "부정 미확정" 409는 ADR-019로 계약에서 빠졌으므로 목업에서 재현하지 않는다. 2026-10-12 확정 범위는 GD-172에서 목업·Zod에 반영했다 — AD05는 사유 trim 후 1~1000자(`awardCancellationRequestSchema`)·UUID `Idempotency-Key`, AD09는 `DrawExecutionResponse`(`runId`·`status`·`confirmation`), 최초 재개 `POST /admin/draws/{runId}/resume`(본문 없음, 확정 200·미확정 202·REPLACEMENT/취소 이벤트 409, 비관리자 403 — `X-User-ID`가 있고 가상 사용자 ADMIN이 아니면 403)는 `features/runDraw`의 `useResumeDraw`가 호출하고, 추첨 상세의 FAILED 최초 실행에 '최초 추첨 재개' 버튼이 있다. 시드 `adm-906`(adminEvent 목업에도 등록)은 최초 추첨이 실패해 재개를 기다린다. AD05·AD09도 비관리자는 403이고, 미확정 REPLACEMENT가 있으면 다른 당첨의 새 취소는 409다. 오류 코드 문자열 `CANCEL-001`~`CANCEL-004`는 GD-169로 계약 확정됐다(404/409/400 매핑 포함).
- 추첨 관리 화면의 "정책 미확정" 표시(GD-125) — 단일 최초 발표·발표 대기·고정 예정 시각 없음은 정책이 확정됐다. GD-199는 PR 구현의 병합·배포·FE 연동 후속이며 새 발표 API를 설계해야 하는 미결정과 구분한다. 관리자 상세는 `execution.latestFailure`·`failureCount`·`retryAt`·`waitingForOperator`·`cancellations[]` 요약과 `GET /admin/draws/{drawId}/failures`·`execution-audits`의 `Page` 이력을 제공하는 현행 모델이다. 실행 감사의 `actorId`는 시스템 처리에서 null일 수 있고 `beforeData`·`afterData`는 JSON 객체가 아닌 nullable 문자열이다. `DrawResult.wasPublished`는 공개 이력, `isCanceled`는 취소 여부이며 현재 명단 포함 여부와 혼동하지 않는다. `PublicListChange.executions[]`는 실행별 확인·취소 근거다. 이는 AU01/AU02 공통 감사 조회 부활이나 미확정 관리자 계약 전체 채택이 아니다. 장애·정합성 오류의 나머지 복구·취소 전환과 발표 후 사용자 중간 표시는 기존 후속·제외 범위를 유지한다(`05-api/drawing.md`, ADR-024)
- 관리자 이벤트 계약 — `entities/event`와 `mocks/handlers/adminEvent.ts`는 `05-api/event.md`의 AE01~AE05·AE08을 따른다. R2 정렬(`createdAt`·`startsAt`·`endsAt`·`title`, 동률 id 같은 방향), 가중치 boolean, KST 등록일 양끝 포함 검색과 `EVENT-008`을 반영했다. `drawScheduledAt`은 관리자 모델·목업에 반영됐고 `publicationScheduledAt`은 제거됐다. AE05 삭제·AE08 취소 계약과 배너 행 보존을 반영했으므로 계약 확인 요청은 해소했다. 배포 존재 확인과 실제 데이터 삭제·반환 성공 검증은 구분한다. AE06·AE07 중단·재개는 ADR-015로 제외됐다.
- 배너 이미지 형식·용량 제한 — 담당자 확정 대기(`pending-decisions.md`의 배너 절 — 제안 수치는 미채택). 이미지를 DB에 키로 저장하고 사용자 응답을 공개 기준 주소 URL로 만드는 분리는 ADR-023으로 확정됐다. 관리자 배너 화면(GD-126)의 안내 문구용 임시값(JPG·PNG·WebP, 5MB)을 `entities/banner/model/policy.ts`의 `BANNER_IMAGE_TEMP_POLICY` 한 곳에만 두었고, 업로드를 막는 검증에는 쓰지 않는다. 이미지 업로드·변환 계약이 없어 폼은 `imageKey`를 직접 입력받는다. 확정되면 이 상수와 폼 안내 문구만 고친다
- 배너 계약 — B01·AB01~AB05가 2026-10-15 사용자 채택됐다(ADR-023, `05-api/banner.md`). `BannerWrite`는 `eventId`·`imageKey`(공백 제거 후 1~500자)·`displayOrder`이고, 등록은 1~N+1 위치 삽입 시 기존을 뒤로 밀고(N=5면 409 `BANNER-004`), 삭제하면 빈자리를 당긴다. AB05는 현재 전체 ID를 중복 없이 받아 원자 반영하고 불일치·동시 목록 변경은 409 `BANNER-005`다. `AdminBanner`는 `createdBy` 없이 `imageKey`·`createdAt`·`updatedAt`을 더하며 이전 URL 배너에 한해 `eventId=null`을 허용한다. 사용자 B01은 이벤트 미연결 이전 배너와 삭제·취소 이벤트 연결분을 제외한 `displayOrder ASC, id ASC`다. 취소 이벤트의 신규 연결은 409 `BANNER-007`. 2026-10-16 선택에 따라 이전 URL·행·이미지 키·생성/수정 시각은 보존하고 URL에서 이벤트 ID를 추측하지 않는다. 미연결 이전 배너도 관리자 목록과 최대 5개에 포함하며 기존 순서는 마이그레이션으로 덮어쓰지 않고 이후 관리 변경 때 상대 순서를 1~N으로 정리한다. 신규 등록·수정의 `eventId`와 사용자 응답의 `eventId`는 계속 필수다. `entities/banner`·`mocks/handlers/banner.ts`에 1기반 순서·nullable eventId·이벤트 삭제/취소 시 관리자 행 보존을 반영했고, 사용자 화면의 배너 슬라이더를 이벤트 목록에서 B01로 전환하는 것은 후속이다
- 가상 사용자 관리 화면(`/admin/virtual-users`, GD-126) — 조회와 현재 세션 사용 여부 확인만 제공한다. 가상 사용자의 수정 가능 범위와 `INACTIVE` 처리가 미확정이라 생성·수정·삭제·상태 필드를 만들지 않았다. 데이터 출처 `/virtual-users`는 spec에 없는 시연 전용 경로다(위 항목). 관리자 사용자 조회 AO01(`GET /admin/users`)·AO02(`GET /admin/users/{userId}`)는 2026-10-15 확정(GD-206)된 별도 계약이다 — `AdminUser`는 id·name·role·status·membership·createdAt·updatedAt 7개 필드만 제공하고 연락처·정지 정보는 없다(오류 `USER-008`~`010`). spec은 `/virtual-users`를 AO01/AO02로 대체하지 않는다고 명시하므로 이 화면은 시연 계정 출처를 유지한다

- 타꼬런 계약(GD-158, 2026-10-16 채택) — `05-api/game-takko-run-draft.md`의 A안·`TAKKO_RUN`·고정 120Hz·xorshift32·`validationData.endTick`·`inputs[].tick/type`(`press`/`release`)을 따른다. - 미션 계약 — M01~M04가 현행 구현 범위로 명세에 반영됐다. - 응모 요청·영수증 모델(GD-133·GD-134, 2026-10-11) — 요청은 `ticketCount:int`가 아니라 등급별 장수 맵 `tickets`(`{"GOLD":1,"SILVER":1}`)이고, `EntryReceipt`에는 `requestedTicketsByGrade`·`deductedTicketsByGrade`가 추가된다. 가중치 미적용 이벤트는 `{"BRONZE":1}`만 허용하고 브론즈 부족은 `ENTRY-008`로 구분 안내된다. 멱등키는 UUID로 응모 요청 결과(접수 또는 저장된 거절)의 ID와 같다. 업무 거절 중 `ENTRY-002·003·005·006·007·008`·`TICKET-006`은 이력에 저장해 E05/E06에서 `status=REJECTED`·차감 장수 0·`acceptedAt=null`로 조회한다(GD-145) — 같은 키의 같은 거절 재전송은 상황이 바뀌어도 최초와 같은 4xx·오류 코드를 돌려준다. 형식 오류(`ENTRY-001`)·없는 이벤트(`ENTRY-004`)·`ENTRY-009`·인증 실패·429는 저장하지 않는다. 응모 429는 `COMMON-006`+`Retry-After`(남은 초)로 사용자 분당 20회·같은 이벤트 분당 10회다(GD-146, 현행 코드). 현재 목업에도 거절 이력 저장과 E05/E06의 REJECTED 조회가 반영됐다. 거절 이력은 GD-145·GD-200 현행 계약으로 해소했으며 별도 미정 계약으로 남기지 않는다. 사용자 응모 오류 코드는 `ENTRY-001`~`ENTRY-009`, 관리자 조회 권한은 `ENTRY-010`, 등급별 보유 부족은 `TICKET-006`. `EntryEligibility.availableTicketBalance`는 해당 이벤트에서 실제 쓸 수 있는 장수(미적용 이벤트는 브론즈 장수)다. `features/enterEvent`·`mocks/handlers/entry.ts`·타임래플 상세(등급별 스테퍼·E07 연동)는 GD-150에서 이 계약으로 전환했다 — 목업 E07도 같은 판정으로 `GET /events/{id}/eligibility`를 제공한다
