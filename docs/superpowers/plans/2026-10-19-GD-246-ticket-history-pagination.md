**목표:** R08 중 T02의 자동 전체 커서 수집만 제거하고, 명시적인 더보기와 정확한 기간 합계를 제공한다.

**구조:** 기존 TanStack Query v5의 `useInfiniteQuery`로 이력을 페이지 단위로 보관한다. 합계는 T02의 조건별 `totalElements`를 별도 `useQueries`로 조회한다. 서버 데이터의 별도 전역 저장소는 만들지 않는다.

**기술:** 기존 React, TypeScript, TanStack Query, Zod, Vitest, Testing Library, MSW. 의존성·설정 변경 없음.

**명세:** `../getddo-spec/05-api/ticket.md`, `../getddo-spec/05-api/common.md`.

## 조회·캐시·복구 결정

- 일반 이력: `useTicketHistories({size:5, operationType?, from?, to?})`. 최초 1요청, 더보기 1회당 다음 커서 1요청. 끝까지 자동 순회하지 않는다.
- 키: `[..., TICKETS_KEY, 'histories', 'infinite', {size,operationType,from,to}]`라는 의미의 기존 tickets 접두사 확장 키를 사용한다(실제 배열은 `[...TICKETS_KEY, ...]`). 합계는 별도 `'count'` 키와 `{operationType,from,to}`를 쓴다. 일반 query와 infinite query의 데이터 형태를 혼용하지 않는다.
- 동일 조건은 같은 캐시를 공유한다. 기간 경계는 가상 시계를 사용하고 화면 진입·필터 변경 시 고정한다. 렌더마다 달라지는 현재 시각을 키에 넣지 않는다. 가상 시간 이동과 일·월 경계에서는 새 조건을 만든다.
- 필터 변경은 해당 조건의 최초 커서에서 시작한다. 이전 필터 데이터를 placeholder로 표시하지 않는다. 기존 조건으로 복귀할 때 그 조건의 캐시를 재사용할 수 있다. 요청에는 AbortSignal을 전달한다.
- 받은=GRANT, 쓴=USE. 만료·반환은 서버가 단일 operationType만 지원하므로 EXPIRE·REFUND 두 스트림을 사용한다. 각 스트림을 size=5로 조회하고 미소비 버퍼를 유지하여 `createdAt DESC,id DESC` 순서로 5개씩 병합한다. 캐시 안에 커서·버퍼·종료 상태를 함께 보관한다. 최초/더보기당 유형별 최대 1회, 총 최대 2요청이며 임의 다중 유형 파라미터를 추가하지 않는다. 실패 시 페이지를 확정하지 않고 같은 입력 커서·버퍼로 재시도한다.
- 응답의 nextCursor가 현재 또는 과거 요청 커서를 반복하면 다음 자동 진행을 차단하고 오류 안내를 표시한다. 같은 id 행은 한 번만 표시한다. 중복 커서로 전체 수집이 재개되거나 무한 루프가 생기지 않는다.
- 빈 items인데 nextCursor가 있는 비정상 페이지도 자동 순회하지 않는다. 안전한 중단·재시도 안내로 처리한다.
- 최초 오류: 빈 결과와 구분하고 다시 시도 버튼을 제공한다. 다음 페이지 오류: 기존 목록과 필터를 유지하며 아래에 재시도 버튼을 표시한다. 재시도는 첫 페이지부터 재수집하지 않는다.
- 더보기 버튼은 요청 중 비활성화하고 `fetchNextPage({cancelRefetch:false})` 및 동기 중복 실행 방어로 연타를 막는다. 이력/합계 조회는 자동 retry를 끄고 사용자 재시도로 요청 수를 명확히 한다.
- 그룹은 페이지를 합친 뒤 기존 groupTicketHistories로 다시 계산한다. 페이지 경계에서 같은 응모가 나뉘면 로드 후 수량이 증가할 수 있으므로 '불러온 이력 기준 수량' 안내를 표시한다. 5건은 원시 이력 기준이며 화면 5개 그룹을 채우기 위해 추가 요청하지 않는다.
- 합계는 size=1로 첫 페이지만 조회하고 totalElements만 사용한다. 일부 로드된 items나 그룹 수를 월·일 전체 합계로 사용하지 않는다. 로딩·오류·실제 0을 구별하고 실패한 합계는 '조회 실패' 및 재시도를 제공한다. 서로 다른 요청 사이의 원자적 스냅샷은 현행 API가 보장하지 않는다.
- 기존 tickets 접두사 무효화와 사용자 전환 시 캐시 정리 흐름이 새 키에도 적용되는지 검증한다.

## 요청 수 예측 — 아직 실행 측정 아님

T02만 계산한다. T01·미션·응모 API는 제외한다. 이전 호출 수는 응답 페이지가 정상적으로 size=100을 채우는 고정 데이터 기준이다.

| 전체 원시 이력 | 이전 전체 수집 | 변경 후 일반 최초 | 더보기 1회 후 누적 |
| -------------- | -------------- | ----------------- | ------------------ |
| 0              | 1              | 1                 | 1 (버튼 없음)      |
| 5              | 1              | 1                 | 1 (버튼 없음)      |
| 6              | 1              | 1                 | 2                  |
| 1000           | 10             | 1                 | 2                  |

| 화면                            | 변경 후 최초 T02 요청 수 | 반환 행 상한 |
| ------------------------------- | ------------------------ | ------------ |
| 미션: 이력+지갑 월 합계         | 1+4=5                    | 5+4=9        |
| 겟또타임: 지갑 월 합계          | 4                        | 4            |
| 내 응모권: 기본 이력+월 받은/쓴 | 1+2=3                    | 5+2=7        |
| 마이페이지: 최근 7일+오늘 받은  | 1+1=2                    | 5+1=6        |

소량 이력에서는 합계 분리로 최초 요청 수가 증가할 수 있다. 1000건에서는 전체 이력 1000행 대신 위 고정 상한만 받는다. 동일 조건의 캐시 공유로 실제 요청은 줄 수 있다. 월 합계 4요청 자체를 1요청으로 줄이는 서버 집계 API는 이번 범위에 포함하지 않는다.
