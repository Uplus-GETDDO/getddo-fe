# 제품 맥락 (product-context)

> 원 기획서(노션 'LG유플러스 응모 이벤트 플랫폼' 종합 기획 문서, 2026-09-18 편집본)에서 공용 명세 저장소 `getddo-spec`에 없는 기획 맥락만 발췌한 문서다.
> **기능·도메인 정책의 기준은 `../getddo-spec/`이다.** 아래 시나리오·비기능에 정책 관련 표현이 spec과 다르면 spec을 따른다.
> 2026-10-20 공용 명세 `bbbe811` 기준으로 계약 변경을 반영했다. FE 구현·배포 상태는 [연동 현황](backend-integration-status.md), 남은 작업은 [통합 로드맵](superpowers/plans/2026-10-20-backend-integration-roadmap.md)을 따른다.
>
> 기획서 원문 이후 spec에서 확정·변경된 주요 사항 (이 문서의 원문 표현과 다를 수 있음):
>
> - 업무 기준일·기준월은 KST(매일·매월 1일 00:00 KST 초기화). 원문의 "00:00 UTC 초기화"는 폐기됨
> - 최초 추첨은 마감 + 1분에 자동으로 진행하되, 최초 공개는 관리자 육안 검토 후 발표 요청 한 번으로 최종 확인 기록·전체 명단 공개를 함께 처리한다 (카운트다운·고정 발표 예정 시각 없음, 화면은 '결과 발표 대기'). ADR-022가 자동 최초 발표를 대체하고 2026-10-15 보완으로 확인·공개 별도 요청 해석도 대체. ADR-026(2026-10-21)이 대기 시간을 5분에서 1분으로 대체
> - 일반 가중치 적용 이벤트의 응모권 사용은 사용자당 이벤트별 누적 최대 5장 — ADR-010
> - 추첨 가중치는 차감한 등급 응모권의 장당 가중치(브론즈 1·실버 3·골드 5·플래티넘 10) 합산으로 계산하고 실제 장수와 구분한다. 별도 가중치 상한·추가 배율은 없다(ADR-014·025). 실제 장수 기준 사용 상한은 ADR-010을 유지한다.
> - 게임·미션 보상은 브론즈·실버·골드·플래티넘 응모권 1장을 무작위 지급한다(79.98/18/2/0.02%, ADR-025). 미션 보상 수량의 관리자 임의 설정은 폐지됐고 출석은 브론즈 고정이다. 기존 무등급 응모권 전환·적용 시점은 미결정 사항을 따른다.
> - 응모 시 사용자가 등급별 장수를 고르는 `tickets` 맵 요청으로 바뀜. 가중치 미적용 이벤트는 브론즈 1장만 차감하고, 반환은 같은 응모권이 등급 그대로 돌아옴 — GD-133 (2026-10-11)
> - 응모 멱등 키는 UUID이며 응모 요청 결과(접수 또는 저장된 거절)의 ID와 같다. 업무 거절은 E05/E06에 `REJECTED`로 저장·조회되고 같은 키의 거절 재전송은 최초 4xx를 재반환 — GD-134·GD-145
> - 응모권 회수(부정 획득분 포함)는 이번 버전에서 제외 — ADR-017 (2026-10-07)
> - 어뷰징 대응은 응모권 지급 전 서버 검증·차단 기록과 관리자 조회로 전환. 관리자의 참여 허용·추첨 제외 결정, 제외 사유 안내, 제외에 따른 응모권 반환은 폐지됨. '추첨 대상자 없음' 종료와 본인 `EXCLUDED` 결과도 신규 계약에서 제외 — ADR-018 (2026-10-11). 응모 요청 반복 초과의 자동 일시 차단(10분)과 이력 조회 AR01/AR02는 GD-141·ADR-027(2026-10-21)로 추가 확정
> - 응모권 API는 응모권 한 장=한 행의 `tickets`·`ticket_histories` 모델로 갱신됨 (`GET /tickets/me`, `GET /tickets/histories/me`). 용어는 '잔액·지갑'이 아니라 '보유 응모권' — 2026-10-10
> - 재추첨은 별도 수동 실행이 아니라 당첨 취소 요청(사유 필수)과 함께 등록되어 서버가 즉시 시작함. 최초 공개 전 취소·재추첨이 있으면 유지 결과와 최종 재추첨 결과를 합쳐 단일 발표 요청에서 실행별 최종 확인·전체 공개를 함께 처리하며 일부 명단을 먼저 공개하지 않음 — 최초 발표 요청에서 최종 확인·전체 명단 공개를 함께 처리(ADR-022의 2026-10-15 보완) — `02-domain/drawing.md`
> - 개별 당첨 취소는 관리자 사유만으로 가능하며(어뷰징 확인 불필요) 응모권을 반환·회수하지 않음, 전체 당첨 취소·전체 재추첨은 추후 추가 예정 — ADR-019 (2026-10-12)
> - 이벤트 등록 시 경품·당첨 인원 동시 등록(함께 성공/실패), 시작 전·진행 예정 상태에서만 수정 가능하며 시작 시각은 앞당길 수 없음 — ADR-011·012
> - 이벤트 일시 중단·재개와 중단 시간 설정은 제공하지 않음 (관리자 취소·응모권 반환은 유지) — ADR-015 (2026-10-06)
> - 이벤트 삭제 시 연결 배너는 자동 삭제되지 않고 관리자가 수동 삭제함 — ADR-021 (2026-10-14)
> - 배너는 이벤트 ID로 연결하고 순서 1~5를 삽입 밀기·삭제 당기기로 관리하며, 삭제·취소 이벤트 연결분은 사용자에게 숨기고 관리자 목록에는 보존함. 이미지는 저장소 키↔공개 URL 분리. 이전 URL 배너는 2026-10-16 선택에 따라 보존하고, 이벤트 미연결이면 사용자에게 숨기되 관리자 목록에는 `eventId=null`로 남기며 최대 5개에도 포함함. 신규 등록·수정의 이벤트 ID는 필수다. B01·AB01~AB05+BANNER-001~008 채택 — ADR-023·`02-domain/banner.md`·`05-api/banner.md`
> - 공통 감사 로그 조회(AU01/AU02)와 전용 화면은 이번 버전에서 제외 — 감사 기록 저장은 유지하고 개별 업무의 운영 내역 조회는 해당 계약을 따른다 — ADR-024 (2026-10-15)
> - 당첨자 표시는 마스킹한 이름(외자는 성만, 그 외 첫·끝 글자)과 전화번호 끝 4자리 — 이메일은 화면·응답 모두 제외 (2026-10-14 확정)
> - 발표 후 취소~명단 갱신 사이의 취소자 임시 표시·본인 중간 결과는, 이번 운영에서 발표 후 취소·재추첨을 사용하지 않는 전제로 GD-140 범위에서 제외 (관리자 API는 유지)
> - 게임 보상은 한 판의 서버 판정 점수가 게임별 최소 보상 점수(타꼬런 400·글자색깔 맞추기 50) 이상일 때만 지급 자격 — ADR-020 (2026-10-12)
> - API 계약 상태는 `../getddo-spec/05-api/`의 도메인별 문서를 따른다. 타이밍·주문 G03/G04는 2026-10-18 채택됐고 AO01에는 2026-10-19 `totalUserCount`가 추가됐다. GD-199는 PR 대조 계약이므로 현재 병합·배포를 새로 확인한다. 계약 채택·BE 구현·FE 연결·배포 검증을 구분한다.
> - 발표 결과는 마스킹한 이름과 전화번호 끝 4자리로 표시하고 이메일은 제외 (닉네임 정책 대체)
> - 임직원 여부는 응모 제한 조건으로 사용하지 않음 (관리자만 응모 불가)

## 프로젝트 목표

**LG유플러스 사이트와 결합**하여, LG유플러스 멤버십 가입자를 대상으로 한 응모 이벤트 플랫폼. 사용자는 출석·미션·게임으로 응모권을 모으고, 이를 응모권 사용 이벤트에 차감해 응모하거나 응모권 미사용 이벤트에 자유롭게 응모하며, 실행별 스냅샷과 저장된 결과를 관리자가 사후에 정합성 검증할 수 있는 구조로 설계한다.

## 타겟층

**LG유플러스 기존 가입자 전체**를 핵심 타겟으로 한다. 별도의 신규 회원 모집이나 특정 등급 고객에 한정하지 않고, 이미 유플러스 서비스를 이용 중인 모든 멤버십 등급의 가입자가 응모 대상이다. 이벤트별 응모 자격(멤버십 등급 등)은 개별 이벤트 설정에서 유연하게 제한할 수 있으나, 서비스 자체의 잠재 사용자군은 전체 가입자로 정의한다.

- 앱/웹을 통해 일상적으로 출석·미션·게임에 참여하며 꾸준히 응모권을 모으는 데 익숙한 사용자
- 특정 시간대에 열리는 한정 이벤트(응모권 사용 이벤트)에 실시간으로 응모하는 사용자
- 추첨 결과와 당첨 과정의 신뢰성을 중요하게 여기는 사용자

## 문제 정의

기존 이벤트 응모·추첨 서비스는 **당첨자가 어떻게, 어떤 기준으로 선정되었는지 사용자가 확인할 방법이 없다는 불투명성 문제**를 안고 있다. 추첨 로직이 공개되지 않고, 추첨에 사용한 후보·조건과 확정 결과의 정합성을 확인할 근거가 없기 때문에, 결과 발표 이후 "조작된 것 아니냐"는 불신이 반복적으로 제기된다. 또한 응모권(포인트성 재화)의 지급·차감 내역이 불투명하게 관리되는 경우, 보유량과 이력이 어긋나는 문제도 사용자 신뢰를 해치는 요인이 된다.

해결 방안으로 **"검증 가능한 공정한 추첨"**을 핵심 설계 원칙으로 삼는다.

- 추첨에 사용된 응모자 명단, 응모권 수, 가중치, 조건을 스냅샷으로 별도 보관해 추첨 시점의 상태와 확정 결과를 대조할 수 있게 한다
- 시드·입력 순서 보존이나 난수 재실행으로 같은 당첨자를 재현하는 요구는 두지 않는다. 관리자는 저장된 스냅샷과 결과로 인원·후보 유효성·중복 당첨·실행 이력을 검증하고, 동일 실행 재요청에는 저장 결과를 반환한다 (`../getddo-spec/03-decisions/001-drawing-consistency.md`, `02-domain/drawing.md`)
- 응모권의 지급·차감 이력은 수정·삭제 없이 누적 기록하며, 이력 합계와 현재 보유 응모권 수가 항상 일치하도록 설계해 "내가 왜 이 응모권을 못 쓰게 됐는지" 같은 불신 요소를 제거한다
- 결과 발표 전에는 철저히 비공개로 유지하고, 발표 시점에는 마스킹된 당첨자 명단과 당첨 경품을 투명하게 공개한다
- ~~어뷰징이 탐지되더라도 자동으로 배제하지 않고, 관리자가 사유를 확인·기록한 뒤 결정하도록 해 임의성을 줄인다~~ (관리자의 추첨 제외 결정은 ADR-018로 폐지 — 어뷰징 대응은 지급 전 차단 기록과 관리자 조회로 전환)
- 발표 후 자격 미달이 확인되면, 해당 당첨만 취소하고 재추첨하되 이력과 최초 추첨과의 연결 관계를 보존해 사후 검증이 가능하게 한다

공통적으로, 위 서비스들은 **혜택·참여 유도 장치는 정교하지만 추첨·선정 과정의 투명성과 사후 검증 가능성은 사용자에게 노출하지 않는다**는 공백이 있다. 본 프로젝트는 포인트·응모권을 돈에 준해 다루는 **커머스형 경품 이벤트**를 소재로 하되, 구매·결제 연계 없이 출석·미션·게임 기반의 무료 참여 구조를 택했다는 점에서 구별된다.

## 차별점

이 과제가 다루는 것은 궁극적으로 포인트·응모권처럼 **돈에 준해 다뤄야 하는 데이터의 정합성**이다. 백엔드는 수정·삭제 없는 이력 설계와 실행별 스냅샷·확정 결과로 사후 정합성을 검증하는 추첨 설계를, 프론트엔드는 이벤트 참여 화면부터 운영자용 백오피스까지 이어지는 실무형 서비스 UI를 함께 구현한다.

## 사용자 시나리오 및 유저플로우

> 원문 시나리오 중 추첨·발표 관련 단계는 spec이 세 번 바꿨다 — ADR-009의 마감 + 5분 자동 발표를 거쳐, 2026-10-14 ADR-022로 "자동 추첨 + 관리자 명단 확인 후 수동 최초 공개"가, 2026-10-21 ADR-026으로 자동 추첨 대기가 +1분으로 확정됐다. 아래 "수동 추첨"은 현재 정책이 아니며(추첨은 자동), "발표"는 관리자 수동 공개 요청으로 읽는다. 카운트다운·고정 발표 예정 시각은 없다. 정책 기준은 `../getddo-spec/02-domain/drawing.md`를 따른다.

### 사용자(응모자) 시나리오

**시나리오 A — 응모권 미사용 이벤트에 응모하기**

1. 가상 사용자를 선택해 로그인 화면을 통과한다.
2. 홈 화면에서 배너 또는 이벤트 목록을 통해 진행 중인 응모권 미사용 이벤트를 발견한다.
3. 이벤트 상세에서 응모 기간·경품·당첨 인원·응모 자격(멤버십 등급)을 확인한다.
4. 응모 자격을 충족하면 '응모하기'를 눌러 경품 선택 없이 이벤트 자체에 응모한다 (응모권 차감 없음).
5. 내 응모 내역에서 응모 처리 결과(접수 완료)를 확인한다.
6. 마감·자동 추첨·관리자 육안 검토·단일 최초 발표 이후, 결과 확인 알림을 받고 당첨 여부와 경품을 확인한다.

**시나리오 B — 응모권을 모아 응모권 사용 이벤트에 응모하기**

1. 기본 출석(하루 1회)으로 응모권을 1장 지급받는다.
2. 미션(설문·퀴즈)과 연속 출석을 수행해 추가 응모권을 지급받는다.
3. 게임을 플레이해 점수를 기록하고, 서버가 유효로 판정한 한 판이 최소 보상 점수(타꼬런 400점·글자색깔 맞추기 50점) 이상이면 사용자별·게임별 하루 1회 한도 내에서 등급 응모권 1장을 지급받는다.
4. 내 응모권 화면에서 보유 수량과 지급·차감 이력을 확인한다.
5. 모집 시작 시각에 맞춰 응모권 사용 이벤트 상세에 진입한다.
6. 가중치 적용 이벤트라면 '응모하기'를 여러 번 눌러 응모권을 그때그때 차감하며 응모를 누적한다 (누적 최대 5장). 가중치 미적용 이벤트라면 1회만 응모하고 브론즈 응모권 1장이 차감된다 (GD-133).

> 응모 차감은 사용자가 등급별 장수를 고르는 방식으로 확정됐다(GD-133, 2026-10-11). "여러 번 눌러 1장씩" 표현은 화면 흐름 예시이며 실제 차감 선택 UI는 계약을 따른다.

7. 모집 마감 후 자동 추첨이 진행되고, 관리자가 명단을 확인해 수동 공개하면 알림함에서 결과를 확인한다.

**시나리오 C — 낙첨·이벤트 취소 등 예외 상황**

> 추첨 제외 흐름은 ADR-018(2026-10-11)로 폐지됐다 — '추첨 대상 제외', '제외 사유 안내', '추첨 대상자 없음' 종료는 신규 계약에 없다. 아래는 기획서 원문 시나리오다.

- ~~어뷰징으로 추첨 대상에서 제외된 경우: 본인에게만 제외 사실과 사유가 안내되며, 일반 낙첨과 구분된 문구로 표시된다.~~ (ADR-018로 폐지 — 어뷰징 대응은 지급 전 차단 기록과 관리자 조회로 처리)
- 접수 완료된 응모자가 없어 이벤트가 '응모자 없음'으로 종료된 경우: 해당 상태가 이벤트 상세·내 응모 내역에 표시된다.
- 이벤트가 취소된 경우: 상태 표시와 함께 차감된 응모권이 반환 이력으로 응모권 내역에 나타난다. (이벤트 일시 중단은 ADR-015로 제외됨)

### 관리자 시나리오

**시나리오 D — 이벤트 개설부터 발표까지**

1. 백오피스에서 이벤트를 등록한다 (이름·설명·이미지·응모 기간·경품·당첨 인원·멤버십 등급 조건·응모권 사용 여부·가중치 적용 여부·모집 시작/마감 시각).
2. 시작 전 상태에서 설정을 검토·수정한다.
3. 진행 중에는 실시간 응모 현황(응모자 수·응모 건수·차감된 응모권 수)을 모니터링한다.
4. ~~마감 후 5분의 검토 시간에 어뷰징 탐지 건을 처리해 '참여 허용' 또는 '추첨 대상 제외'를 결정하고 사유를 기록한다.~~ (ADR-018로 폐지 — 마감 후 1분은 자동 추첨의 실행 기준이며(GD-268), 어뷰징은 지급 전 차단 기록 조회로 대응한다)
5. 마감 시각 + 1분에 시스템이 자동으로 최초 추첨을 실행하고, 관리자가 명단을 육안으로 검토한 뒤 발표 요청 한 번으로 최종 확인·전체 명단 공개를 함께 처리한다 (ADR-022, 대기 시간은 ADR-026).
6. 실제 공개에 연결해 응모자 전원의 결과 확인 알림 작업을 등록하고 비동기로 생성한다. 발표 응답은 전체 알림 생성을 기다리지 않는다.

**시나리오 E — 발표 후 재추첨**

> 관리자 사유에 따른 개별 당첨 취소·빈 자리 재추첨은 ADR-019(2026-10-12)로 확정됐다. 어뷰징·자격 미달 확인은 필수 조건이 아니며 응모권을 반환·회수하지 않는다. 전체 당첨 취소 후 처음부터 재추첨은 추후 추가 예정이다. 지급 후 게임 점수 무효화는 `pending-decisions.md`의 "지급 전 차단 전환의 후속 확인"에 따른다. 단 이번 운영은 발표 후 취소·재추첨을 사용하지 않는 전제이며, 그 사이 취소자 임시 표시·본인 중간 결과는 구현하지 않는다(GD-140 범위 제외). 관리자 기능·API 자체는 유지된다.

1. 발표 후 관리자가 특정 당첨을 취소해야 한다고 판단한다 (자격 미달·부정 확인은 필수 조건이 아니다).
2. 관리자가 사유를 입력하고 해당 당첨만 취소한다 (다른 당첨자는 유지). 이 사유가 재추첨의 업무 근거로 보존된다.
3. 취소 확정과 함께 연결된 재추첨 실행이 등록되어 서버가 즉시 시작하고, 결과는 최초 추첨 이력과 연결되어 보존된다.
4. 관리자가 재추첨 결과를 확인한 후 수동 공개로 당첨자 명단을 갱신하고, 당첨 취소자와 새 당첨자에게만 변경 알림이 생성된다 (공개는 결과 확정·확인 저장만으로 진행되지 않는 명시적 요청이다).

> 최초 공개 전에 취소·재추첨이 발생하면 유지 결과와 최종 재추첨 결과를 합쳐 발표 요청에서 필요한 실행별 최종 확인 기록과 전체 명단 공개를 함께 저장하고, 미확정 결과나 일부 명단을 먼저 공개하지 않는다 — 고정 발표 예정 시각이 없고 공개 자체가 관리자 수동 요청이다(ADR-022) — `../getddo-spec/02-domain/drawing.md` 결과 발표 절.

### 1. 김도윤 — 데일리 루틴러

**기본 정보**

**IT/앱 사용 습관**
알림을 켜두고 오는 대로 바로 반응하는 편이며, 아침 출근길·점심시간·잠들기 전 하루 세 번 정도 앱을 연다. 루틴처럼 반복되는 행동(출석·간단한 미션)에 익숙하고 거부감이 없다.

**목표(Goals)**

### 페르소나 활용 가이드

- **화면 우선순위**: 김도윤·박서연 유형은 응모권 사용 이벤트와 응모권 내역 화면의 완성도가 경험을 좌우하므로, 실시간 응모 현황과 응모권 이력 화면을 우선 다듬는 것을 권장한다.
- **신뢰 요소 노출**: 이하늘 유형을 고려하면 추첨 결과 안내와 낙첨 사유 문구를 명확히 설계하는 것이 중요하다 (추첨 제외 안내는 ADR-018로 폐지).
- **진입 장벽 최소화**: 최민준 유형을 고려하면 응모권 미사용 이벤트의 응모 흐름을 최대한 단순하게 유지하고, 배너에서 이벤트 상세까지의 클릭 수를 최소화하는 것을 권장한다.
- **가중치 정책과의 관계**: 박서연 유형(타임어택 헌터)의 경험은 가중치 계산식에 직접 영향을 받는다. 가중치는 차감한 등급 응모권의 장당 가중치(브론즈 1·실버 3·골드 5·플래티넘 10) 합산이며 실제 장수와 구분한다(ADR-014·025). 일반 이벤트의 누적 5장 상한은 실제 장수 기준이다. 골드 5장의 가중치는 25다. 월말 소진용 예외는 명세의 운영 조건을 충족할 때만 적용한다.

## 운영 및 시연 범위 (원 기획서 15절)

원문의 더미 데이터는 시연용 계정·이벤트를 뜻한다. 현재 목표는 서버에 등록된 격리 시연 데이터를 사용하고 배포 브라우저의 가짜 업무 응답을 제거하는 것이다. 테스트용 MSW와 시연 계정 선택은 유지하며, FE 가상 시계가 서버 시간·추첨·공개를 바꾸지는 않는다.

- 로그인 화면에서 사용자 또는 관리자 역할을 선택해 진입하는 시연 흐름을 제공한다.
- 가상 사용자 선택·전환으로 사용자별 데이터를 시연한다.
- 가상 사용자와 더미 데이터로 시연하며, 동일 가상 사용자는 고정된 사용자 ID로 식별한다.
- 시연 인증 및 관리자 보호는 아래 비기능 요구사항의 시연 로그인·관리자 보호 기준을 적용한다.
- 시간 저장·비교는 UTC를 기준으로 하고 화면에서는 KST로 표시한다. 일일·월간 업무 기준일은 KST로 판정한다.
- 응모권 지급·지급 전 검증부터 응모·자동 추첨·관리자 육안 검토·단일 최초 발표·정합성 검증까지 더미 데이터로 시연한다.
- 보유 응모권 부족, 중복 요청, 지급 전 차단, 결과 발표 대기, 낙첨, 응모자 없음, 이벤트 취소 등 예외 상황을 포함한다. 추첨 제외·전원 제외 종료는 제공하지 않는다(ADR-018).
- 더미 데이터에서도 이력·잔액·응모·추첨 결과의 정합성을 유지한다.
- 로딩, 빈 목록, 오류, 처리 성공 등 화면 상태를 안내한다.
- 실제 외부 알림 발송, 배송·결제는 이번 범위에서 제외한다.
- 주간 미션은 보류한다. 주간 미션·주간 랭킹의 기준 시각은 해당 기능 도입 시 정한다.

## 프론트엔드 연동 계약 (원 기획서 16절)

FE-BE 연동은 `../getddo-spec/05-api/`의 개별 채택 범위와 현행 구현 표기를 따른다. 아래 정책 확정·계약 채택·현행 구현은 배포·FE 연동 완료와 구분하며, 나머지 검토 대기 초안은 확정 정책처럼 적용하지 않는다. 전체 목록과 코드 차이는 [CONTEXT.md](CONTEXT.md)의 '백엔드 연동 전 임시 상태'를 따른다.

- [확정] 사용자 알림 N01~N03·관리자 알림 AN01~AN05 — `05-api/notification.md`. 알림은 마감 +1분·추첨 완료가 아니라 관리자의 발표 요청으로 실제 공개될 때 발생한다(2026-10-17 문구 동기화, 대기 시간은 GD-268)
- [확정·채택] 배너 B01·AB01~AB05, 관리자 사용자 AO01·AO02, 관리자 응모권 AO03·AO04·AO05·AO08·AO09, 사용자 결과 E08·E09, 추첨 GD-87·GD-138 일부·GD-169 선택 범위, 어뷰징 조회 AR01/AR02(채택·배포·실측 완료), 게임 G01·G02·G05 및 색깔·타꼬런·타이밍·주문 G03/G04를 따른다. AO01의 `totalUserCount`는 필터와 무관한 현재 활성 일반 사용자 수이며 검색 건수 `totalElements`와 구분한다. E01 목록의 `winnerCount`는 경품 인원 합계다(GD-251)
- [확정 정책·병합·배포됨] 최초 발표는 육안 검토 후 `POST /admin/draws/{runId}/result-confirmation` 한 번으로 최종 확인·전체 공개를 함께 처리한다. 별도 확인 버튼·선행 확인 호출·최초 발표의 `publication` 추가 호출은 없다. GD-199는 PR #108로 2026-10-17 병합·배포됐고 FE는 GD-253에서 연결했다. 본문·추가 멱등 헤더 없는 최신 검토 `runId`·기존 DTO/오류·성공 재시도 계약은 `05-api/drawing.md`를 따른다
- [현행 구현] 미션 M01~M04·AM01~AM05, 응모 E03~E07·AO06·AO07, 출석 AT01~AT03·AP01~AP06, T01·T02와 U01 비활성 거절(403 `USER-007`) — `05-api/mission.md`·`entry.md`·`attendance.md`·`ticket.md`·`user.md`. 미션 보상은 1장 고정이며 관리자 등록도 생략 또는 1만 허용한다
- [확정·구현 예정] 관리자 응답의 사용자·처리자·작성자 이름 필드(ADR-028)는 추첨·응모·알림·응모권 정합성·미션·출석 DTO에 추가됐다. BE 구현·배포 전이며 ID가 null이면 이름도 null이다
- [공통 현행·개별 계약 우선] 응답 봉투는 `success/code/message/data`, 실패는 실제 4xx·5xx와 `data=null`이다. `Page`는 `items/page/size/totalElements`(page 1부터), `Cursor`는 `items/nextCursor/totalElements`이며 `totalPages`·`hasNext`는 없다. 공통 문서의 size 기본 20·범위 1~100은 제안이므로 개별 계약의 채택·현행 값을 우선한다(`05-api/common.md`)
- [사용자 문맥 결정·현행 구현] 모든 업무 API는 등록된 `X-User-ID`·`X-User-Role`을 필수로 받는다. `X-User-Membership`은 USER의 멤버십 조건 API에서 필수이고 그 외 선택이며, 전달하면 DB 값과 대조한다. 권한은 DB 역할로 판단하고 헤더로 승격하지 않는다. 이 방식은 신원 인증이 아닌 통제된 시연용 문맥 전달이다(`05-api/common.md`)
- [현행 구현·개별 계약 우선] 응모·미션 제출은 UUID `Idempotency-Key`를 사용한다. 같은 본문의 성공 재시도는 저장 결과 200, 저장된 응모 거절은 최초 4xx·오류 코드를 반환한다. 다른 본문은 409 `ENTRY-009`·`MISSION-005`다. 출석은 사용자·KST 업무일, 채택 게임은 서버 발급 `playId`로 구분한다. AD05 전역 취소 키와 최초 발표 재시도는 `05-api/drawing.md`를 따르며 모든 관리자 생성 요청에 공통 멱등 응답을 약속하지 않는다
- [현행 구현] 요청 빈도 제한은 429 `COMMON-006`과 `Retry-After`(1분 고정 창의 남은 초)다. 응모는 사용자 분당 20회·같은 이벤트 10회, 출석은 5회, 미션 제출은 사용자 20회·같은 미션 5회다. 게임 결과의 분당 10회 정책은 정의됐고 컨트롤러 적용은 후속이며, 수치는 운영 설정값이다(`05-api/common.md`)
- [2026-10-18 채택·구현 후속] 타꼬 타이밍은 현재 FE 규칙·최소 50점, 타꼬 주문은 현재 FE 규칙·최소 18점과 기존 게임 공통 저장·통계·보상 흐름을 따른다. FE 연동·교차 검증·DB 등록·배포는 별도다.
- [미확정 유지] 배너 이미지 허용 형식·용량, 지급 전 차단 상세 계약, 기존 무등급 응모권 전환·적용 시점, 개인정보 파기·보존의 상세 방식은 `00-requirements/pending-decisions.md`를 따른다.
- 실시간 응모 현황 갱신 주기는 구현 담당자 재량이다(`00-requirements/functional-requirements.md` 7절). 공통 감사 조회 AU01·AU02와 전용 화면은 제외하고 기록 저장·추첨 업무별 실행 이력은 유지한다(`03-decisions/024-audit-recording-without-query.md`, `05-api/drawing.md`)

## 비기능 요구사항

> 원 기획서의 비기능 요구사항 원문. spec의 기능 정책과 다른 표현이 있으면 spec을 따른다 (예: "관리자 발표 승인"은 ADR-009 자동 발표를 거쳐 ADR-022의 관리자 수동 공개로 정리됐다).

### 1. 사용자 규모 및 요청량

- 이벤트당 응모자: 1,000명.
- 동시 접속자: 100명.
- 평시 요청량: 초당 20건(20 RPS).
- 마감 직전 요청량: 초당 100건(100 RPS)을 1분간 유지.
- 동시 접속자와 초당 요청량은 별도로 측정한다.
- 테스트 전에 조회·응모 요청 비율과 데이터량을 고정한다.

### 2. 응답 시간 및 실시간 발표

- 조회 API: p95 500ms 이하.
- 응모 API: p95 1초 이하.
- 실시간 발표: 관리자의 발표 요청으로 실제 공개된 후 접속 사용자 화면 반영까지 p95 2초 이내(원문 성능 목표). 고정 발표 예정 시각 도달을 공개 조건으로 삼지 않는다(ADR-022).
- 재접속한 사용자는 결과 조회 API로 발표된 결과를 확인한다.
- 발표 전 결과는 재접속·직접 조회로도 공개하지 않는다.
- p95는 전체 측정값의 95%가 해당 시간 이내라는 의미다.

### 3. 동시성 및 데이터 정합성

- 출석·미션 보상은 중복 지급되지 않아야 한다.
- 동시 응모에도 응모권 잔액이 음수가 되지 않아야 한다.
- 출석 기록과 보상 지급은 함께 성공하거나 함께 취소되어야 한다.
- 응모 기록과 응모권 차감은 함께 성공하거나 함께 취소되어야 한다.
- 최초 추첨과 각 재추첨 실행은 요청이 중복되어도 각각 하나의 결과만 확정되어야 한다.
- 마감 시 처리 중인 응모의 기준을 정하고, 추첨 대상 확정 후에는 해당 스냅샷을 변경하지 않는다.
- 초기에는 DB 트랜잭션·유일 제약·조건부 차감을 적용하고 부하 테스트 결과에 따라 보강한다.

### 4. 부하 테스트 합격 기준

- 테스트 도구: k6.
- 평시 테스트: 20 RPS로 10분간 유지.
- 마감 집중 테스트: 100 RPS로 1분간 유지.
- 응답 시간: 조회·응모 API별 목표 충족.
- 예상하지 않은 오류: 전체 요청의 1% 미만.
- 정합성 오류: 중복 지급·초과 차감·중복 결과 확정 0건.
- 마감·잔액 부족 등 정책에 따른 정상 거절은 시스템 오류와 구분한다.
- 같은 사용자의 동시 응모와 중복 요청을 별도로 검증한다.
- 서버·DB 사양, 데이터량, 요청 비율을 테스트 결과에 기록한다.

### 5. 시연 로그인 및 관리자 보호

- 역할 선택 로그인은 데모 환경에서만 활성화한다.
- 현행 시연은 별도 로그인 API 없이 등록된 사용자 ID를 헤더로 선택한다. 역할·멤버십은 서버 DB 값과 대조하며, 이 방식 자체는 신원 인증이 아니다(`05-api/common.md`, `user.md`). 외부 공개 운영의 인증은 이 시연 계약과 구분한다.
- 사용자 역할은 서버에서 결정하며 클라이언트가 전달한 역할 값을 그대로 신뢰하지 않는다.
- 모든 관리자 API는 서버에서 인증·권한을 검사한다.
- 인증되지 않은 요청은 401, 권한이 없는 요청은 403으로 응답한다.

### 6. 이미지 저장소 및 배포 환경

- 이미지 저장소: S3 등 객체 저장소를 사용한다.
- DB 저장 정보: 이미지 파일 대신 저장소 키를 저장한다.
- 업로드 권한: 관리자만 허용한다.
- 배너 이미지 허용 형식·파일당 용량 제한은 담당자 미확정이다. 원문의 JPEG·PNG·WebP 및 5MB는 채택되지 않은 제안이며 확정 제한으로 사용하지 않는다(`00-requirements/pending-decisions.md`, `02-domain/banner.md`).
- 초기 배포 구성: 애플리케이션 1대 + DB.
- 실행 환경: Docker 기반.
- 통신: HTTPS를 적용한다.
- 비밀정보는 환경변수 또는 시크릿 관리 기능으로 관리하며 저장소에 커밋하지 않는다.

### 7. 로그·모니터링·백업

- 요청 로그: 요청 ID, API 경로, 응답 상태, 처리 시간.
- 오류 로그: 예외 내용, 요청 ID.
- 운영 감사 기록: 추첨 시작·재개·당첨 취소·정책 변경의 처리자, 시각, 사유를 보존한다. 추첨 대상 제외는 폐지됐고 공통 감사 조회 API·전용 화면은 제외한다. 추첨 업무별 실행 이력은 해당 API로 조회한다(ADR-018·ADR-024, `05-api/drawing.md`).
- 모니터링: CPU·메모리 사용량, 오류율, 응답 시간, DB 연결 수.
- 민감정보 보호: 비밀번호·인증 토큰 기록 금지, 개인정보 마스킹.
- DB 백업: 일 1회 수행, 7일 보관.
- 복구 검증: 시연 전 백업 데이터 복구를 확인한다.

### 8. 결과 발표 및 응모자 알림

- 결과 발표와 개인별 알림 생성을 분리한다.
- 최초 결과가 공개되면 응모자 전원 알림은 비동기로 생성한다 (원문의 "관리자 발표 승인"은 ADR-009 자동 발표를 거쳐 ADR-022의 관리자 수동 공개로 정리됐다 — 알림은 실제 공개에 연결).
- 발표 상태 변경과 알림 생성 작업 등록을 같은 DB 트랜잭션에 저장해 작업 누락을 방지한다.
- 별도 작업자가 응모자를 나누어 처리하고 실패한 작업은 재시도한다.
- 이벤트·사용자·알림 유형을 기준으로 중복 생성을 방지한다.
- 발표 후 명단 갱신 시 알림은 당첨 취소자와 새 당첨자에게만 생성한다 (spec 알림 규칙 기준).
- 알림 생성 목표: 응모자 1,000명 기준 결과 공개 후 30초 이내.
- 재시도 후에도 실패한 작업은 기록하고 운영자가 재처리할 수 있어야 한다.
- 실제 문자·메일 발송은 제외하고 모의 발송과 처리 결과 기록까지 구현한다.
- 실시간 발표는 응모자 전원의 알림 생성·발송 완료를 기다리지 않는다.
