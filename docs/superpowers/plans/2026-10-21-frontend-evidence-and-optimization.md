# 페르소나 기반 프론트엔드 정량 검증·최적화 작업 계획서

> 실행자는 `executing-plans` 스킬로 작업을 순서대로 수행한다. 단계별 체크박스와 증거를 갱신하며, 사용자 요청 없이 별도 에이전트나 새 채팅을 만들지 않는다.

**목표:** 페르소나 요구 → 구현 판단 → 재현 가능한 측정 → 발표 문장으로 연결하고, 측정으로 확인한 병목과 중복 처리 결함만 개선한다.

**구조:** 현재 구현과 과거 증거를 먼저 분리한다. 동일 조건의 기준선과 개선 후 결과를 보존하며, 요청 감소·화면 성능·업무 정합성·개발 효율을 서로 다른 지표로 다룬다.

**기술:** 기존 React·TypeScript·TanStack Query·MSW·Vitest·Testing Library, 설치된 Node와 브라우저 도구를 재사용한다. 새 의존성은 전제하지 않는다.

**명세:** [제품 맥락](../../product-context.md), [연동 현황](../../backend-integration-status.md), `../getddo-spec/00-requirements/`, `../getddo-spec/02-domain/`, `../getddo-spec/05-api/`. 경로의 `../getddo-spec`은 프론트엔드 저장소 루트 기준이다. 확정 공용 명세가 기획 원문·이미지보다 우선한다.

**조사 기준:** 2026-10-21 KST, `dev` / `12e95e98ea36c51d2a1f3197c21794bcc6436d70`. 조사 시작 시 작업 트리는 깨끗했다. 이번 작성에서는 제품 코드 변경·성능 실행·실서버 요청을 하지 않았다. 아래 숫자는 기존 보고서 또는 코드에서 확인한 기록이며 현재 커밋의 재측정값이 아니다.

### 정책·근거 구분

- 이미지의 김도윤 요구에 있는 `09:00 KST 초기화`는 과거 내용이다. 공용 `02-domain/attendance.md`는 **00:00 KST**, 현 `MissionListPage.tsx`는 **매일 자정 초기화**를 표시한다. 발표용 인용은 현재 정책으로 정정하고 원본 이미지 변경은 별도 산출물로 다룬다.
- 이미지의 ‘제외 사유’는 현재 추첨 제외 기능으로 구현하지 않는다. ADR-018 이후 정책과 응모 거절·낙첨·미공개 상태를 구분한다. 무작위 추첨의 개인별 낙첨 원인을 만들어 설명하지 않는다.
- ‘가중치 적용 이벤트’와 빠른 참여 욕구가 선착순·먼저 누를수록 높은 당첨 확률을 뜻하지 않는다. 확정 가중치 규칙을 따른다.
- 현재 구현과 니즈가 대응한다는 사실만으로 ‘개발 당시 이 페르소나 때문에 결정했다’고 단정하지 않는다. 관련 커밋·PR·기획 기록을 확인하고 없으면 **페르소나를 기준으로 현재 구현을 점검했다**고 쓴다.
- 가상 인물·에이전트 시연은 실제 사용자 조사 결과가 아니다. 사용성 개선 효과를 주장하려면 사람의 과제 수행 기록을 별도로 수집한다.

## 3. 범위와 승인 경계

- 이 문서는 계획·프롬프트 작성 요청에 대한 산출물이다. 실행 프롬프트를 사용자가 새 세션에 직접 전달하면 아래 기존 코드 범위의 조사·측정·조건부 최적화 승인을 전달한 것으로 본다.
- 실행 시 `git branch`·`git status`와 최신 AGENTS.md·명세를 다시 읽는다. `main`·`dev`에는 커밋하지 않는다. 기존 적합한 작업 브랜치를 재사용하고, 없으면 실제 Jira 키를 확인한다. Jira 키를 만들지 않는다. 키가 없으면 읽기 조사·증거 수집을 먼저 하고 구현용 브랜치만 질문한다.
- 새 의존성, DB schema, API contract, auth, 상태관리·라우팅·폴더 등 아키텍처 패턴, eslint·tsconfig·빌드 설정, 환경변수 변경은 별도 명시 승인 대상이다. 라우트 lazy 확대·`vite.config.ts` 수정도 후보와 근거를 먼저 제시한다.
- 미사용 라이브러리 제거·새 측정 패키지 설치·CI 수정도 자동 실행하지 않는다. 기존 설치 도구가 없으면 동등한 수동 DevTools 측정 또는 도구 승인 요청을 사용한다.
- 운영 쓰기·부하·반복 응모·429 유도·추첨/발표는 이 계획으로 승인되지 않는다. 기존 검증 스크립트의 `misc`는 출석 40회 쓰기를 포함하므로 읽기 성능 측정용으로 실행하지 않는다. 과거 보고서의 승인을 새 세션에 승계하지 않는다.

## 5. 측정 계약

### 5.1 공통 기록과 재현 조건

- 각 실행에 `runId`, KST/UTC 시각, `commit`, 변경 파일 diff 식별자, Node·브라우저 버전, OS·CPU·메모리, URL·빌드 모드, viewport·DPR, CPU/네트워크 제한, cache, 환경(local-mock/staging/production), fixture ID·건수, 계정 역할을 기록한다. 계정 식별자는 익명화한다.
- 프론트 성능은 production build/preview를 기본으로 한다. dev+MSW 검증은 기능·요청 수용으로 분리하며 production 수치와 비교하지 않는다. preview API 연결 방법은 기존 설정을 확인한다. 기존 설정으로 재현 불가하면 임의 환경변수 추가 없이 차단 조건을 적는다.
- 비교는 같은 장비·브라우저·데이터·응답 지연·API 모드로 한다. 콜드/웜 캐시는 각각 따로 수집한다. 빌드 산출물과 실제 네트워크 전송량은 별개 지표다.
- 로딩은 경로별 콜드 10회·웜 10회, 동작 시간은 시나리오별 30회, 로컬 API 정합성 fixture는 시나리오별 독립 초기화 100회로 시작한다. 반복이 비용·데이터를 만드는 경우 로컬에서만 실행한다.
- 중간값·p95·최솟값·최댓값·IQR·실패 수·표본 수를 함께 남긴다. n=10의 p95는 사실상 극단값이므로 탐색적 수치로만 표시한다. 임의로 유리한 표본을 빼지 않는다.
- API 응답 실패를 지연 성공 표본에서 뺐다면 실패율과 제외 이유를 반드시 별도로 보고한다. baseline에 없던 실패는 성능 개선으로 수용하지 않는다.
- 원시 HAR·trace의 토큰·쿠키·사용자 ID·응답 개인정보는 저장 전 제거한다. 필요한 timing·바이트·상태만 보존하는 방식을 우선한다.

집계 규칙은 다음 순수 함수와 동등해야 한다. 단위는 시간 ms, 크기 byte, 비율 %다.

```js
function p95(samples) {
    if (!samples.length || samples.some((x) => !Number.isFinite(x))) return null;
    const sorted = [...samples].sort((a, b) => a - b);
    return sorted[Math.ceil(sorted.length * 0.95) - 1];
}
function reductionPercent(before, after) {
    if (!Number.isFinite(before) || !Number.isFinite(after) || before <= 0) return null;
    return ((before - after) / before) * 100;
}
```

집계 테스트는 `[1..100] → p95 95`, `[1..30] → p95 29`, 빈 배열·NaN → null, `10→1 = 90%`, `100→85 = 15%`, `25→20 = 20%`, `0→0 = null`을 검증한다. 환경/fixture/cache가 다르면 개선율을 계산하지 않고 `not-comparable`로 남긴다.

**최종 수용 기준:** 측정 조건과 원시 자료로 숫자를 재현할 수 있고, 성능 개선으로 업무 정확성이 낮아지지 않으며, 모의 검증을 운영 효과로 확대하지 않는다. 목표 미달·차단 항목이 남으면 전체 목표 달성으로 보고하지 않는다.
