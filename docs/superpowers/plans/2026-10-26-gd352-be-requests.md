# BE 담당자 요청 — GD-352 통합 검증 잔여 (2026-10-26)

`docs/backend-integration-status.md`의 미확정·미관측 잔여 중 FE가 스스로 해소할 수 없는 항목이다.
2026-10-26 GD-352 읽기·승인 쓰기 실측(reports/20261026-gd352-*) 기준으로 정리했다 — 이미 해소된 항목은 제외하고, 실측으로 새로 확인된 질의도 포함한다.

## 요청 항목

### R1. 추첨 시나리오 C1~C6 격리 이벤트 제공

- **필요한 것**: BE 관리자 컨텍스트에서 준비된 격리 이벤트 6종 — ①미공개 확정 ②취소 가능 당첨 ③FAILED 실행 2형태(재시도 가능/불가) ④취소 ⑤응모자 없음 ⑥응모자가 시연 계정 소유인 이벤트.
- **이유**: 관리자 추첨 실서버 기능 검증(응답 DTO 표본·실패 재개·재추첨·알림-결과 일치)이 시드 데이터 대기 중이다. FE가 임의로 만들면 운영에 영구 잔존(삭제 API 부재)하므로 BE 측 시드를 요청한다.
- **담당자 후보**: 추첨 담당 (석종수 추정 — 확인 필요).

### R2. 발표→알림 생성 도착 트리거 검증 협조

- **필요한 것**: 격리 이벤트에서 최초 공개(`result-confirmation`)를 실행해 알림이 응모자에게 도착하는 흐름을 유발하거나, 해당 트리거가 연결된 격리 환경을 제공한다.
- **이유**: N01~N03·linkUrl·빈 목록은 배포 실측 완료(GD-331). "공개→알림 생성"의 트리거 연동만 서버 이벤트 없이 유발할 수 없어 미관측이다.
- **담당자 후보**: 알림 담당 (전민규 추정 — pending-decisions 기준).

### R3. 503 `COMMON-007` 운영 배포 여부·장애 시험 일정

- **필요한 것**: BE PR #176(DB 연결 장애 → 503 `DB_TEMPORARILY_UNAVAILABLE`)의 운영 배포 여부와, 실제 503을 받아볼 장애 시험(이중화 전환 등) 일정 또는 재현 방법.
- **이유**: FE는 GD-335에서 5xx 멱등키 유지·공개 문구 매핑을 구현했고 프록시 차단으로 재현 검증했으나, 실서버 503 표본은 미관측이다.
- **담당자 후보**: 인프라/공통 담당.

### R4. 배너 실서버 CRUD 격리 환경 + 이미지 업로드 계약 확정

- **필요한 것**: ① 실데이터를 건드리지 않고 AB01~AB05 CRUD를 시험할 격리 환경 또는 테스트 배너 슬롯 ② 이미지 업로드 API·허용 형식·파일당 용량의 확정(pending-decisions "담당자 추후 확정" 항목 — JPG·PNG·WebP·5MB 등 제안 수치는 미채택 상태).
- **이유**: B01 조회·홈 슬라이더·목업 CRUD는 검증됐으나 실서버 CRUD 통합 검증과 업로드 계약이 미확정이다. 현재 운영 배너 5개는 실데이터라 임의 변경 불가.
- **담당자 후보**: 배너 담당 (윤태형 추정 — 확인 필요).

### R5. `[TEST-GD261]` 잔여 데이터 정리 방법

- **필요한 것**: 운영에 남은 `[TEST-GD261]` 이벤트 2건·미션의 정리 방법 — 삭제 API가 없어 FE가 임의로 처리할 수 없다. BE 측 직접 삭제·비공개 처리 또는 방치 승인 중 결정이 필요하다.
- **이유**: GD-261 쓰기 인수의 성공 생성분. 출석 정책 2건은 10-22에 원복됐으나 이벤트·미션은 잔존한다.

### R6. INACTIVE 사용자·추첨 FAILED 실행 표본 생성

- **필요한 것**: ① `status=INACTIVE` 사용자 계정 1건(비활성 사용자의 로그인·응모·조회 거절 계약 실측용) ② FAILED 상태의 추첨 실행 표본 또는 실패를 유발하는 방법(실패 재개·재시도 표시 검증용).
- **이유**: 2026-10-26 재확인에서도 관리자 사용자 100명 전원 ACTIVE, 추첨 실행 72건 전부 CONFIRMED/NO_ENTRIES — 두 표본 모두 자연 발생하지 않아 미관측 유지다.
- **담당자 후보**: 사용자/추첨 담당.

### R7. EVENT 차단 표본의 이벤트 연결 확인 (신규 질의)

- **관측 사실**: 2026-10-26 AR02 상세에서 `triggerScope=EVENT` 표본 1건을 확인했다 — evidence 계약 필드(ruleVersion·windowStartedAt/EndsAt·requestLimit·rejectedCount·rejectionThreshold)는 모두 존재하나 `eventId`·`eventTitle`이 null이다.
- **필요한 것**: 이벤트 기준 차단 건의 `eventId`·`eventTitle`이 계약상 채워져야 하는지 확인 — 채워져야 한다면 표본이 계약과 다른 원인(구 데이터·연결 누락)을 확인해 달라.
- **이유**: 관리자 어뷰징 상세가 이벤트 링크를 표시하는 계약이라, EVENT 표본의 연결 필드 부재는 화면 표시 계약과 직결된다.

### R8. 배송 정보 입력 — 계약 제안 또는 범위 제외 확정

- **상황**: `product-context.md`는 "배송·결제는 이번 범위에서 제외"로 표기하는 반면, FE `pages/timeRaffleDetail/ui/WinnerBanner.tsx`에는 배송 정보 입력 버튼(TODO, 계약 없음)이 존재한다. 공용 명세 `05-api`에도 수령 정보 엔드포인트가 없다.
- **필요한 것**: 양자택일 확정 — ① 수령 정보 API를 spec으로 제안해 범위에 포함하거나 ② 범위 제외를 확정해 FE가 버튼을 제거·비노출 처리한다.
- **이유**: 문서 간 충돌이라 FE가 임의로 판단할 수 없다.

### R9. 자정/월 경계 정책 적용 관측 계획

- **필요한 것**: 일일 출석(KST 자정)·연속 출석·응모권 만료(월 1일 KST 자정)의 정책 적용 시점 전환을 관측할 방법 — 경계 시점에 변경이 걸린 예약 데이터나, 서버 시각을 관측 가능한 시연 환경.
- **이유**: 시점 의존이라 FE가 임의로 유발할 수 없다. 관측 설계만 정리하면 되므로, 다음 자정/월 경계 전에 예약 정책 데이터가 준비돼 있는지 확인해 달라.

### R10. 결과 성능 목표 측정 설계 협조

- **목표**: 발표→사용자 화면 반영 p95 2초·알림 생성 30초(원 기획서 비기능 요구사항).
- **측정 설계안**: 격리 이벤트(R1의 C1 활용)에서 발표 시각 `t0`를 기록하고, ① 응모자 계정의 `GET /v1/events/{id}/results`가 `isPublished=true`를 반환하는 시각 `t1` ② `GET /v1/notifications/me`에 해당 알림이 도착하는 시각 `t2`를 측정한다. `t1-t0`이 화면 반영 지연(폴링 주기 30초 상한), `t2-t0`가 알림 생성 지연이다. 서버 측 발표 완료 시각을 알려주면 클라이언트 폴링 지연과 서버 처리 지연을 분리할 수 있다.
- **필요한 것**: 측정용 격리 이벤트 + 발표 실행 시각 통지(또는 발표를 관찰할 관리자 화면 접근).

### R11. (낮은 우선도) 일일 출석 미래 예약 표본

- **필요한 것**: AP01 일일 정책에 미래 `effectiveFrom` 예약 1건(현재 3건 전부 적용 중·과거라 AP05 200 측정 대상이 없다).
- **이유**: AP02 생성은 삭제 API 부재로 영구 잔존하므로 FE가 임의 생성하지 않는다 — BE 측 시드 또는 임시 데이터가 적합하다. 연속 출석 미래 `effectiveMonth` 표본은 이미 있어 AP06은 측정 완료다.
