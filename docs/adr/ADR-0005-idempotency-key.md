# ADR-0005: 중복 위험 요청에 멱등키 적용

- 상태: accepted
- 날짜: 2026-09-17

## 맥락

응모·추첨은 되돌리기 어려운 부작용을 만든다. 네트워크 재시도나 더블클릭으로 같은 요청이 두 번 가면 응모가 중복 생성되거나 응모권이 이중 차감될 수 있다. 클라이언트에서 버튼 비활성화만으로는 재시도를 막을 수 없다. 공용 명세도 "같은 요청의 재시도와 새로운 응모를 구분해 중복 반영을 방지한다"고 명시한다 (`../getddo-spec/02-domain/entry.md`) — 응모권 차감이 없는 미사용 이벤트 응모에도 적용된다.

## 결정

재시도·중복 클릭으로 같은 부작용이 두 번 생기지 않도록 작업별 중복 식별 계약을 따른다. 멱등 헤더를 요구하는 요청에는 `shared/utils/idempotencyKey`의 `createIdempotencyKey()`로 생성한 UUID를 `IDEMPOTENCY_HEADER` 헤더에 붙인다. 모든 POST에 일괄 적용하지 않는다.

- 대상 계약: `POST /events/:eventId/entries`(응모 — 사용·미사용 이벤트 모두), `POST /missions/:missionId/submissions`(미션 제출), AD05 `POST /admin/wins/:winId/cancellations`(당첨 취소). 공통 기본 경로 `/api/v1`은 생략했다
- 헤더명은 `05-api/common.md`의 `Idempotency-Key`다(2026-09-30 `X-Idempotency-Key`에서 교체). 공통 문서 전체는 검토 대기지만 응모·미션의 현행 구현과 AD05 채택 범위에서 사용하는 헤더를 다시 미확정으로 취급하지 않는다
- 작업별 구분은 공통 문서와 개별 채택·현행 구현 계약을 따른다:
    - 응모·미션 제출 → UUID 멱등키. 접수·제출 ID는 키와 같고 성공 재시도는 저장 결과를 200으로 반환한다. 저장된 응모 거절 재시도는 최초 4xx·오류 코드를 그대로 반환하며, 같은 키·다른 본문은 각각 409 `ENTRY-009`·`MISSION-005`다. 마감 뒤 재시도도 기존 결과를 유지한다
    - 출석 → 사용자·KST 기준일로 재처리되므로 멱등키를 쓰지 않는다. 같은 날 재요청은 서버가 200으로 기존 결과를 돌려준다
    - 채택된 글자색깔·타꼬런 게임 결과 → G03 서버 발급 `playId`로 G04 재시도를 식별한다. 최초 확정 결과·점수·보상을 재사용하며 처리 중이면 202다. 타꼬 타이밍·타꼬 주문의 상세 규칙·보상 점수는 검토 대기다
    - AD05 → 전역 키와 같은 관리자·당첨 대상·정규화 사유를 대조한다. 다른 관리자·대상·내용으로 재사용하면 409 `CANCEL-003`이며 기존 취소·연결 재추첨을 중복 생성하지 않는다
    - AD09·최초 재개 → 이미 연결된 실행 ID를 사용하며 추가 키를 요구하지 않는다. GD-199 단일 최초 발표 PR도 본문·추가 멱등 헤더 없이 최신 검토 `runId`를 사용한다. 최초 공개에 사용한 같은 실행의 성공 재시도는 최초 공개 버전을 반환하지만 이후 취소·삭제 등 공개 불가 상태는 거절한다(`05-api/drawing.md`, PR 병합 후 적용 예정)
    - 알림 읽음 → 사용자·알림 ID 조합이 자연키라 멱등키를 쓰지 않는다
- 조회(GET)와 이미 멱등인 요청에는 붙이지 않는다

## 결과

- 새로운 부수효과 요청은 개별 계약의 중복 식별 기준을 먼저 확인한다. 관리자 생성 요청에 공통 멱등 응답을 약속하지 않는다. 응모권 회수는 이번 버전에서 제외다(공용 ADR-017)
- MSW 핸들러가 멱등키 누락 시 400을 반환하므로, 목업 환경에서 누락을 바로 발견할 수 있다
- 출석 목업은 멱등키를 요구하지 않고, 같은 기준일 재요청은 확정한 결과를 200으로 재사용한다
