# 백엔드 연동·프로젝트 완성 로드맵

> 실행자는 `executing-plans`로 작업별 계획을 구체화하고 승인된 범위만 구현한다. 이 문서 작성은 구현·배포 승인이 아니다. 서브에이전트는 별도 요청 없이 사용하지 않는다.

**목표:** 송동현 담당 영역을 우선해 배포 중 가짜 업무 응답을 제거하고, 공용 명세의 서비스·관리자 흐름을 실제 백엔드로 완성한다.

**구조:** 기존 FSD·TanStack Query·Zod·공통 오류/시간/멱등 유틸을 유지한다. 도메인별 계약과 화면을 맞춘 뒤 해당 배포 목업을 해제하고, 마지막에 시연 계정 공급과 브라우저 MSW 부팅을 정리한다. 테스트용 MSW는 유지한다.

**기술:** 기존 TypeScript·React·Vite·Vitest 환경을 사용한다. 새 의존성을 전제하지 않는다.

**기준:** FE `a49796a`, getddo-spec `bbbe811`, 2026-10-20. [연동 현황](../../backend-integration-status.md)과 [공용 구현 범위](../../../../getddo-spec/00-requirements/scope.md)를 함께 읽는다. 배포 응답·백엔드 PR 상태는 착수 시 새로 확인한다.

## 범위와 진행 규칙

- 관련 조회·화면·오류·검증을 묶어 **6개 Jira 작업**으로 제안한다. 아래 L1~L6는 문서 내부 번호이며 실제 Jira 키가 아니다. Jira를 생성하거나 담당을 배정한 상태가 아니다.
- 송동현의 기존 응모권·현황·알림·공통 기반·관리자 연동 작업을 중심으로 L1/L2/L3/L6을 제안한다. 게임·미션은 박소연, 이벤트·응모·결과 화면은 장준환과 경계를 조율한다. 이는 Git 이력과 기존 역할을 바탕으로 한 제안이며 현재 Jira 담당을 조회한 결과가 아니다.
- 하나의 Jira 안에서도 조회→행동→통합 검증을 작은 커밋으로 나눈다. 같은 파일을 여러 작업이 바꾸면 먼저 병합된 변경을 반영한다. Jira별 기존 브랜치를 확인하고 한 브랜치에 여러 Jira를 섞지 않는다.
- API contract·사용자 문맥·새 메뉴/라우트·빌드 설정·환경 변수 변경은 프로젝트 승인 규칙을 따른다. 확정된 계약의 소비와 새 계약 제안을 구분한다.
- 매 작업은 실제 HTTP 상태·봉투·Zod·권한을 확인한다. 경로의 400/401/404만으로 정상 연동을 판정하지 않는다. 서버 오류에 샘플 데이터를 대신 보여주지 않는다.
- 테스트 데이터 쓰기는 격리된 시연 계정·이벤트로 수행한다. DB 샘플 데이터 삭제, 운영 데이터 변경, 인증 방식 교체는 이 계획에 포함하지 않는다.
- 전체 제거 대상은 **배포 런타임 목업**이다. Vitest fixture·장애 재현·로컬 개발 목업을 무차별 삭제하지 않는다.
- 공통 감사 조회·참여 허용/추첨 제외·사용자 수정·응모권 수동 지급/회수·실제 문자/메일·전체 당첨 취소 후 처음부터 재추첨은 구현 범위에 추가하지 않는다.

## 권장 순서와 병행 관계

**송동현의 첫 작업은 L1을 추천한다.** 관리자 사용자 조회는 계약과 경계가 명확하고 응모권 운영·대시보드의 실제 사용자 기준을 함께 정리할 수 있다.

1. ~~L1을 시작하며 L2의 최초 발표/차단 계약, L3의 배너 위치를 미리 확인한다.~~ L1(GD-250)·L2 구현(GD-253)은 완료됐다. L3(GD-255)는 사용자 승인으로 위치를 확정해 구현·로컬 인수를 진행했다. L2 실서버 검증 입력 대기는 L6에서 별도로 관리한다.
2. ~~송동현은 L1 → L2 → L3 순서로 진행한다. L2가 외부 계약에 막히면 L3을 먼저 진행한다.~~ L2의 BE 답변 대기 잔여(격리 이벤트 C1~C6·AR01/AR02 계약·알림 통합 검증)는 L3~L6 진행을 차단하지 않는다 — L6 인수 검증 입력으로 이관하고, 답변이 오면 후속 검증 커밋으로 처리한다. 답변이 오지 않으면 L6 완료 조건의 "범위 조정 명시적 결정"으로 사용자 판단을 받는다.
3. L4 게임과 L5 이벤트·미션·출석 완성은 각 담당자와 병행할 수 있다. 송동현은 응모권·알림·공통 요청 경계를 지원한다.
4. L1~L5의 구현·도메인 검증을 끝낸 뒤 L6에서 MSW 없는 배포와 전체 흐름을 인수 검증한다. L6의 구현 작업(계정 공급·MSW 종료·Worker 정리)은 BE 답변을 기다리지 않고 진행한다.

L2의 결과 흐름은 L5의 이벤트 상태 처리와 마지막에 결합하고, L3의 연결 이벤트 이동도 L5의 상태·상세 경로와 맞춘다. L4/L5 보상은 L1의 기존 응모권 조회와 대조한다. `mocks/handlers/index.ts`는 각 작업이 자기 도메인만 변경하고 L6이 최종 점검한다.
