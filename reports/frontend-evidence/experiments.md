# 실험 기록 — 가설·수정·판정

> 계획서 작업 3·4의 기록지다. 최적화를 시도할 때마다 먼저 정확한 파일·책임·기대 지표를 적고, 동일 조건 전후 측정으로 판정한다.
> 이번 세션(test/GD-289-quant-baseline)의 승인 범위는 **기준선 수집**이다 — 기능 코드(`src/` 앱 코드) 수정은 하지 않으므로, 여기에는 측정에서 확인한 후보만 기록한다.

## 판정 규칙

각 실험은 `개선 유지` / `무효` / `철회` / `승인 대기` 중 하나로 끝난다. 지연 지표는 반복 2배치 모두 개선되고 개선 폭이 기준선 IQR보다 클 때 우선 수용한다.

### GD-264 후속 — 브라우저 표본 수집 후 후보별 판정

baseline-r2(`baseline-r2-2026-10-22T06:20Z`, commit `40e9fda`, MSW 활성 production 빌드 + 시스템 Chrome headless)의 ux-* 표본으로 이전 세션이 남긴 후보를 검증했다. 지연 기준은 계획서 §5.2의 내부 후보값(LCP 2.5초, CLS 0.1, 피드백 200ms)이다.

**결론:** 모든 후보가 내부 기준 이내라 측정으로 입증된 병목이 없다. 계획서 규칙("효과가 없으면 코드 변경 없이 종료")에 따라 제품 코드(`src/` 앱 코드)는 수정하지 않았다. 추가한 것은 계측 스크립트·증거 파일·누락 검증 테스트 뿐이다.

## 측정된 후보 (다음 세션 입력)

- 게임·관리자 lazy 경계는 이미 존재(`GamePlayer.tsx`, `adminRoutes.tsx`, `vite.config.ts` 벤더·차트 분리) — 재최적화 대상이 아니며 기존 작업을 새 성과로 세지 않는다. 초기 청크 합계·실전송량은 baseline `bundle-*`이 처음으로 수치화했다.
- `useLoopingBgm.ts`·배너/썸네일 이미지·오디오 선로딩은 브라우저 표본이 있어야 병목 여부를 단정할 수 있다 — GD-264에서 확인한 바로는 게임 진입 LCP p95 1448ms로 기준 이내다 (재검증 완료).
- `entities/event/api/queries.ts`·`entities/entry/api/queries.ts`·`widgets/myEntryRows`의 최초 전체 수집 비용은 rowPolling 테스트가 Axios spy로만 관측한다 — MSW HTTP 경계의 추가 계측이 필요하면 테스트 추가가 먼저다.
- `/missions` 최초 로드의 API 21건·리소스 88건은 결정적 관측치다 — 개별 호출의 업무 목적이 분명하지만, 실서버 지연 조건에서는 지배 비용이 될 수 있다. 실서버 스테이징 계측 후 판단할 후보로 남긴다.
