## 재개 순서

1. 브랜치·미커밋 변경·공용 명세를 확인한다. 인계 당시 별도 `2026-10-21-entry-ticket-display.md` 계획이 나타났으나 이번 GD-262 작업과 커밋에서 제외했다. 다른 작업을 덮어쓰지 않는다.
2. 기존 실행 환경의 Playwright/Chrome을 확인한다. 현재 스크립트는 Codex Windows 번들의 Playwright 경로를 사용한다. **Devin에서는 기존 설치 도구 경로에 맞춰 도구 로딩 부분을 조정**하고, 새 의존성 설치가 필요하면 승인받는다. Python 방식으로 구현되지 않았다.
3. 원본 88f4970과 후보를 분리된 출력 폴더에 프로덕션 빌드한다. 둘 다 기존 MSW 비활성·API base `/api` 등 동일 옵션을 사용한다. .env를 덮어쓰지 않는다. 검증용 사용자 선택에는 기존 실제 등록 계정 설정이 필요하다.
4. 새 호스트라면 임시 파일로 고정 응답을 수집한다. `--capture=true`에서 초기 진입뿐 아니라 부모 화면·미션 모달·추가 이력 커서에 필요한 GET을 확보한다. 사용자 이름/헤더/응답 본문을 보고서·Git에 넣지 않는다. 수집 종료 후 파일을 고정하고 양쪽의 fixtureHash가 같은지 검증한다.
5. 아래 명령을 양쪽 preview에 대해 **직렬로** 실행한다. 원격에서 재수집할 때 기존 partial 자료를 덮어쓰지 않도록 새 label을 사용한다. 핵심 측정 조건·끝점을 바꾸면 양쪽을 모두 다시 실행한다.

- 조회 API p95≤500ms·응모 API p95≤1초·실제 공개→화면 p95≤2초는 기존 문서 목표다. 서로 구간이 다르다. 일반 화면 클릭→표시의 확정 목표는 없어 **미확정**으로 남긴다.
- 실제 발표·응모 쓰기·RUM·서버 내부 처리·사용자 부하는 이번 GET 실험으로 검증하지 않는다.
- E06 전체 합계/결과 필터 요약, E09 다건 조회, M01 questionCount, 게임 목록 통계, 공개→화면 2초와 현재 30초 폴링의 차이는 BE와 계약/정합성 협의가 필요한 후속 후보로 보고서에 분리했다.
- E01 eventType 필터는 별도 실제 GET 검사에서 동일 ID 집합을 확인했다. 기존 계약 활용에 해당하는 FE 후속 후보이며 새 BE 계약 요구와 구분한다. 이번 코드에는 적용하지 않았다.
